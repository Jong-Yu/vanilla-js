DOM 수정은 객체의 어느 부분을 바꿀지 정하는 일입니다

앞 장에서 요소를 찾으면 실제 DOM 객체의 참조를 얻는다는 것을 보았습니다. 이제 그 객체에 새로운 값을 대입할 수 있습니다. 다만 요소는 글자 하나만 담은 단순한 상자가 아닙니다. 문서에 붙은 속성, 자식 노드, 폼 컨트롤의 현재 입력값처럼 서로 다른 정보를 관리합니다. 같은 “바꾼다”라는 말이라도 어느 정보를 대상으로 하는지에 따라 사용해야 할 API가 달라집니다.

예를 들어 p 요소의 안내 문구를 바꾸는 것과 input에 현재 입력된 이름을 바꾸는 것은 다릅니다. p의 문구는 자식 텍스트로 표현되고, 텍스트 입력의 현재 값은 입력 컨트롤이 관리하는 상태입니다. 전자는 textContent로, 후자는 value로 다룹니다. 이 차이를 이해하면 문구를 바꾸려다가 입력값이 그대로인 상황이나, 현재값 대신 초기값을 읽는 상황을 설명할 수 있습니다.

DOM 변경을 이해할 때는 “무엇을 저장하는가”, “어떤 값과 연결되는가”, “브라우저는 그 변경을 어떻게 표시하는가”라는 세 질문을 연결해서 보면 됩니다. 이번 장은 명령을 여러 개 익히기보다 이 연결을 이해하는 데 집중합니다.

왜 attribute와 property라는 두 표현이 있을까요?

HTML에서는 요소를 태그와 속성으로 기술합니다. <input value="민지">의 value="민지"처럼 요소에 붙는 이름과 값의 쌍을 content attribute라고 부릅니다. HTML 문서에 적힌 내용을 선언적으로 표현하는 수단입니다. 브라우저가 요소 객체를 만든 뒤에도 이 attribute는 DOM 안에 존재하며, getAttribute나 setAttribute로 읽고 바꿀 수 있습니다.

한편 JavaScript에서 DOM 객체를 사용할 때는 그 객체가 제공하는 property에 접근합니다. input.value나 input.disabled가 그 예입니다. property는 단순한 문자열 사본일 수도 있지만, 현재 상태를 읽거나 브라우저의 정해진 동작을 수행하는 창구일 수도 있습니다. property를 설정하면 대응하는 attribute가 변경되기도 하고, 별도의 내부 상태가 변경되기도 합니다.

이 두 표현이 연결되는 것을 반영, 즉 reflection이라고 합니다. 예를 들어 요소의 id property를 바꾸면 id attribute도 바뀝니다. title이나 className도 대응하는 attribute와 연결됩니다. 하지만 모든 property가 같은 이름의 attribute를 그대로 반영하지는 않습니다. 어떤 property는 불리언이나 숫자로 변환하고, 어떤 것은 값을 정규화하며, 입력 컨트롤의 현재 상태처럼 기본 설정과 분리된 정보를 제공합니다.

따라서 “attribute는 HTML, property는 JavaScript”라고만 외우면 중요한 부분을 놓칩니다. 둘 다 실행 중인 DOM에서 접근할 수 있습니다. 또한 attribute가 원본 파일의 영구적인 초기값인 것도 아닙니다. setAttribute로 바꾸면 DOM의 attribute가 달라지지만, 디스크에 저장된 HTML 파일까지 수정되지는 않습니다. 지금 어떤 표현을 읽고 있는지가 핵심입니다.

브라우저가 현재값과 기본값을 나누어 관리하는 이유

입력창은 문서를 읽을 때의 설정과 사용자가 편집한 결과를 모두 다뤄야 합니다. HTML의 value attribute는 기본값을 정합니다. 텍스트 입력의 defaultValue property는 이 attribute와 연결됩니다. 반면 value property는 지금 입력창에 들어 있는 문자열을 읽고 씁니다. 사용자가 “민지”를 “하루”로 바꾸면 현재값은 하루가 되어도 기본값은 민지로 남을 수 있습니다.

왜 항상 서로를 똑같이 갱신하지 않을까요? 현재 입력과 기본 설정이 한 값뿐이라면 사용자의 편집을 보존하면서 초기 상태를 따로 관리하기 어렵습니다. 브라우저는 아직 기본값을 따라가는 상태와, 현재값을 직접 설정한 상태를 구분합니다. 이 구분을 위해 내부에 변경 여부를 기록하는 표시가 있으며, 표준에서는 dirty flag라고 부릅니다. 잘못되거나 오염된 값이라는 뜻이 아니라 현재값이 독립적으로 설정되었다는 표시입니다.

사용자가 입력하거나 코드가 value에 대입하면 이 표시가 설정됩니다. 그 뒤 기본값을 바꾸더라도 현재의 편집 결과를 무조건 덮어쓰지 않습니다. 아직 이런 변경이 없는 입력에서는 기본값 변경이 현재값에도 반영될 수 있습니다. 그래서 “attribute를 바꾸면 언제나 현재값도 바뀐다”와 “attribute는 현재값에 절대로 영향을 주지 않는다”는 설명이 모두 정확하지 않습니다.

체크박스도 같은 구분이 필요합니다. checked property는 현재 선택 여부이고, defaultChecked는 checked attribute와 연결된 기본 선택 여부입니다. 사용자가 체크를 해제해도 기본 선택 여부는 유지될 수 있습니다. 폼을 reset하면 컨트롤은 그때의 기본값으로 돌아가고 이러한 변경 표시도 초기화됩니다. 현재 상태를 확실히 지정하려면 value나 checked에 직접 대입하고, 기본 설정을 바꾸려면 defaultValue나 defaultChecked를 구분해서 사용합니다.

현재값·기본값·변경 표시의 관계는 HTML 표준의 input 동작에 정의되어 있습니다.

작은 코드에서 현재값과 기본값을 한 줄씩 읽기

아래 코드는 HTML에 value="민지"가 있는 입력창을 대상으로 합니다. 같은 요소에서 읽는 값이 왜 다른지, 각 줄이 무엇에 접근하는지 따라가 보겠습니다.

const input = document.querySelector("#username");
const before = input.getAttribute("value");
input.value = "하루";
const current = input.value;
const initial = input.defaultValue;
console.log(before, current, initial);
  1. 1행: username 요소 객체를 찾습니다. input은 그 객체를 가리키는 이름입니다.
  2. 2행: DOM의 value attribute를 문자열로 읽습니다. 지금은 “민지”이며 before에는 이때 읽은 문자열이 저장됩니다.
  3. 3행: 컨트롤의 현재값을 “하루”로 설정합니다. 입력창의 현재 표시도 이 값을 사용하고, 기본값의 attribute를 덮어쓰지는 않습니다.
  4. 4행: 현재값을 다시 읽습니다. current는 “하루”가 됩니다.
  5. 5행: value attribute와 연결된 기본값을 읽습니다. initial은 여전히 “민지”입니다.
  6. 6행: “민지”, “하루”, “민지”를 차례로 출력합니다. 하나의 요소가 서로 다른 의미의 값을 관리하고 있음을 보여줍니다.

이후 input.defaultValue = "기본 이름"으로 기본값을 바꾸면 value attribute도 바뀝니다. 하지만 앞에서 현재값을 직접 설정했으므로 현재의 하루는 유지됩니다. before와 initial에 앞서 저장한 문자열도 자동으로 다시 읽히지 않습니다. 요소가 관리하는 상태의 연결 규칙과 JavaScript 변수에 이미 저장한 값의 규칙을 함께 구분해야 합니다.

불리언 상태와 문자열 표기를 구분하기

getAttribute는 속성이 있으면 문자열을, 없으면 null을 반환합니다. 하지만 HTML의 모든 속성이 문자열 내용을 같은 방식으로 해석하는 것은 아닙니다. checked·disabled·required 같은 불리언 attribute는 속성의 존재 자체로 참을 표현합니다. disabled="false"라고 써도 disabled가 존재하므로 비활성 상태입니다. 끄려면 속성을 없애거나 disabled property에 false를 설정합니다.

checked attribute도 존재 여부로 기본 선택 상태를 표현하지만, 현재 선택을 뜻하는 checked property와는 앞서 본 분리가 있습니다. box.checked = false는 현재 선택을 끄는 작업이지 checked attribute를 반드시 제거하는 작업이 아닙니다. 반면 disabled property는 그 attribute의 존재 여부를 반영합니다. 둘 다 불리언 property라는 이유만으로 반영 규칙까지 같다고 생각하면 안 됩니다.

data-* attribute는 요소에 애플리케이션이 사용할 문자열 정보를 기록하는 방법입니다. data-notifications="on"은 element.dataset.notifications로 읽고 쓸 수 있습니다. dataset에 false를 대입해도 저장되는 것은 문자열 “false”입니다. JavaScript의 조건문에서는 빈 문자열이 아닌 “false”도 참으로 평가하므로, dataset.notifications === "on"처럼 약속한 값과 비교합니다.

HTML 불리언 attribute와 data 속성, ARIA 속성을 같은 규칙으로 취급해서도 안 됩니다. 예를 들어 aria-expanded의 “false”는 그 속성에서 정한 의미를 갖는 문자열입니다. 무조건 속성이 있으면 참이라고 해석하지 않습니다. 문자열 표기와 프로그램의 불리언 상태 사이를 어떻게 연결할지는 각 API의 규칙을 따라야 합니다.

내용을 교체해도 모든 객체가 같은 방식으로 바뀌지는 않습니다

요소의 textContent에 문자열을 대입하면 그 요소의 자식 내용을 텍스트로 교체합니다. 부모 요소 객체 자체를 새로 만드는 것은 아닙니다. 하지만 그 안에 있던 강조 요소나 아이콘도 자식이므로 제거될 수 있습니다. 제목에 아이콘과 글자가 함께 있다면 글자를 담당하는 span을 따로 두고 그 span을 수정하는 편이 의도를 정확히 표현합니다.

제거된 자식 객체를 다른 변수가 계속 가리키고 있다면 그 객체는 문서에서 떨어진 상태로 남을 수 있습니다. 같은 태그와 문구로 새 자식을 만들어도 이전 객체와 정체성이 같은 것은 아닙니다. 기존 객체에 붙인 이벤트 리스너나 별도 상태가 새 객체로 자동 이동하지 않습니다. 단순히 최종 화면이 같다는 이유로 어떤 DOM 변경 방법이든 동등하다고 볼 수 없는 이유입니다.

textContent는 입력을 HTML로 해석하지 않습니다. “<strong>하루</strong>”를 넣으면 꺾쇠를 포함한 글자를 표시합니다. 반면 innerHTML은 문자열을 HTML로 파싱하여 자식 구조를 만들거나 교체합니다. 사용자에게 받은 문장을 그대로 보여주는 목적이라면 textContent가 맞습니다. 불필요하게 HTML로 해석하면 의도하지 않은 요소나 위험한 동작을 만들 수 있습니다. 표시할 텍스트와 문서 구조를 만드는 작업을 분리해서 생각하세요.

객체 변경이 화면의 모양으로 이어지는 과정

JavaScript는 class나 data 속성을 바꿀 수 있지만, 그 이름만으로 브라우저가 특정 디자인을 선택하지는 않습니다. CSS 선택자가 현재 요소와 일치하고, 다른 규칙과의 우선순위 및 상속 등을 통해 적용할 스타일이 결정되어야 합니다. data-notifications="on"이라는 값을 썼다고 자동으로 초록색이나 파란색이 되는 것은 아닙니다.

preview.textContent = "알림이 켜져 있어요.";
preview.dataset.notifications = "on";
preview.classList.add("status");

첫 줄은 자식 내용을 바꾸고, 둘째 줄은 data attribute를 바꾸며, 셋째 줄은 class 목록에 status를 추가합니다. 이 페이지에는 status의 글자색과 굵기를 정하는 CSS가 있기 때문에 마지막 변경이 강조된 모습으로 이어집니다. data 속성을 스타일 조건으로 쓰고 싶다면 #preview[data-notifications="on"]과 같은 선택자에 규칙을 작성해야 합니다.

classList는 특정 클래스만 추가하거나 제거하는 창구입니다. className에 새 문자열을 대입하면 기존 클래스 전체가 교체됩니다. 또 인수 하나인 toggle은 현재 상태를 뒤집지만, toggle("status", enabled)는 enabled가 뜻하는 목표 상태로 맞춥니다. 같은 값을 다시 화면에 반영할 때마다 모습이 뒤집히지 않게 하려면 “전환”과 “원하는 상태로 설정”을 구분해야 합니다.

DOM의 값은 코드가 대입한 뒤 바로 읽을 수 있지만, 실제 픽셀을 다시 그리는 과정은 별도의 브라우저 작업입니다. 브라우저는 변경에 따라 필요한 스타일을 계산하고, 필요하면 크기와 위치를 계산한 뒤 화면을 그립니다. 여러 변경이 한 번의 화면 갱신으로 모일 수도 있습니다. 따라서 DOM을 한 줄 바꿀 때마다 반드시 전체 화면을 즉시 다시 그린다고 생각할 필요는 없습니다.

또 코드로 value나 checked를 대입했다고 사용자 입력에 따른 input·change 이벤트가 자동 발생하지는 않습니다. 아래 예제는 값을 읽어 문구를 만드는 updatePreview를 필요할 때 직접 호출합니다. 다음 장에서는 사용자의 행동이 어떻게 이벤트가 되고, 그 이벤트를 받아 어떤 변경 함수를 호출할지 연결하는 과정을 읽습니다.

예제 3-2 · 현재값과 기본값 · value / defaultValue

입력을 바꾸어도 기본값은 남을까요?

예상하기: 이름을 바꾸고 체크를 해제한 뒤 값을 읽으면, HTML에 적힌 기본값도 함께 바뀔까요?



username.value = "지우";
notifications.checked = false;
// username.defaultValue는 "민지"
// notifications.defaultChecked는 true


관찰할 결과: 코드 변경 후 현재값은 “지우”, false이고 기본값은 “민지”, true입니다. 되돌리기는 form.reset()을 호출하므로 기본값이 다시 현재값이 됩니다. 아래 기록은 “읽기”나 코드 변경 버튼을 누른 시점의 값입니다.






예제 3-3 · HTML 불리언 속성 · 존재 여부
disabled="false"는 활성 상태일까요?


예상하기: 아래 입력에 disabled 속성을 문자열 “false”로 붙여보세요. 키보드로 입력할 수 있을까요?







input.setAttribute("disabled", "false"); // 비활성
input.disabled = false; // 속성이 없어지고 활성화


관찰할 결과: 속성을 붙이면 input.disabled는 true입니다. HTML 불리언 속성은 문자열 내용이 아닌 존재 여부를 봅니다. property에 false를 대입하면 속성이 제거됩니다. ARIA의 “false”나 data 속성에는 이 규칙을 그대로 적용하지 않습니다.






예제 3-4 · 상태와 시각 표현 · dataset / classList
data 속성만 바꾸면 색도 바뀔까요?


예상하기: “data 속성에 on 기록”을 누른 뒤 “클래스로 표현 반영”을 눌러보세요. 어느 단계에서 글자색과 굵기가 달라질까요?


알림이 꺼져 있어요.






preview.dataset.notifications = "on";
const enabled = preview.dataset.notifications === "on";
preview.classList.toggle("status", enabled);


관찰할 결과: 이 예제는 data 속성만으로 스타일을 정하는 CSS가 없습니다. 클래스 반영을 누르면 .status 규칙 때문에 강조되고 문구도 바뀝니다. 같은 상태를 다시 반영해도 모습이 뒤집히지 않습니다. 데이터와 화면의 연결은 작성한 코드가 담당합니다.

예제 3-2에서 이름을 바꾸고 체크를 해제한 뒤 “현재값과 기본값 읽기”를 눌러보세요. 현재값은 바뀌지만 기본값을 나타내는 attribute는 남아 있는 이유를 본문에서 찾을 수 있습니다. 더 확인하고 싶다면 코드 변경 버튼에 username.defaultValue 대입을 추가한 뒤 코드를 실행해 현재값과 비교해보세요.
