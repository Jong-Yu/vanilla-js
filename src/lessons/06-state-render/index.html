화면에 나타내는 사실을 어디에 저장하고, 어떤 코드가 그 사실을 DOM에 반영하는지 살펴봅니다. 상태와 파생값, 갱신 함수, 값을 결정하는 주체를 차례로 구분합니다.

상태는 프로그램이 기억하는 현재의 사실입니다

알림이 켜져 있는지, 어떤 탭을 선택했는지, 입력한 문장이 무엇인지처럼 프로그램이 현재 기억해야 하는 값을 상태라고 부릅니다. 특별한 객체 종류나 예약어의 이름은 아닙니다. 불리언 하나, 문자열 하나, 여러 값을 담은 객체 모두 상태를 표현하는 데 쓸 수 있습니다. 중요한 것은 값의 문법보다 그 값이 어떤 사실의 기준이 되는지입니다.

이 장에서 기억할 사실은 알림의 선택 여부 하나입니다. 이를 { checked: false }라는 객체에 담고 state라는 변수로 가리킵니다. false는 알림을 끄겠다는 현재 상태입니다. 객체에 checked라는 속성을 정한 것도, 변수를 state라고 부른 것도 작성자의 선택입니다. 브라우저가 그 이름을 보고 체크박스와 자동으로 연결하지는 않습니다.

한 사실을 여러 방식으로 표현할 수 있습니다. checked가 true이면 체크 표시를 켜고, “켜짐”이라는 문구를 보여주고, data-state에 checked라는 문자열을 쓸 수 있습니다. 원본 값에서 계산할 수 있는 이런 값을 파생값이라고 합니다. 파생값은 별개의 사용자 선택이 아니라 이미 가진 사실을 다른 형태로 표현한 것입니다.

무엇을 원본으로 삼을지 정해야 하는 이유

체크 여부와 “켜짐” 문구를 각각 별도 변수에 저장하면 두 값을 함께 바꿔야 합니다. 한쪽을 빠뜨리면 checked는 false인데 문구는 “켜짐”일 수 있습니다. 같은 사실을 중복 저장해서 서로 어긋나는 문제가 생긴 것입니다. 기준값 하나를 정하고 표시할 문구를 그때그때 계산하면 함께 맞춰야 할 원본의 수가 줄어듭니다.

원본은 언제나 자바스크립트 객체여야 하는 것은 아닙니다. 간단한 폼에서는 사용자가 입력한 DOM의 현재 값을 제출할 때 읽는 것으로 충분할 수도 있습니다. 이 장은 여러 요소가 같은 선택 여부를 보여주고, 사용자 입력과 코드 양쪽에서 값을 바꾸기 때문에 자바스크립트의 state를 기준으로 삼습니다. 화면이 어떤 요구를 갖는지에 따라 상태를 둘 위치를 결정하는 것입니다.

이 결정을 해두면 문제가 생겼을 때 비교할 기준이 있습니다. 체크 표시와 안내가 다르면 state가 무엇인지 먼저 확인하고, 각각의 DOM이 그 값에서 계산되었는지 추적할 수 있습니다. 여러 표시 중 눈에 보이는 것 하나를 임의로 믿는 대신, 어떤 값이 최종 결정권을 가지는지 코드에 드러내는 셈입니다.

자바스크립트 메모리와 DOM의 값 연결하기

state.checked와 input.checked는 서로 다른 객체의 속성입니다. 앞의 것은 우리가 만든 일반 객체의 값이고, 뒤의 것은 브라우저가 제공하는 입력 요소의 현재 선택 값입니다. 둘의 속성 이름이 같거나 처음 값이 같아도 서로 연결되지는 않습니다. 하나를 대입한다고 다른 객체의 속성이 자동으로 바뀌는 규칙이 자바스크립트에 생기는 것은 아닙니다.

연결하려면 한 값을 읽고 다른 위치에 쓰는 코드를 실행해야 합니다. input.checked = state.checked가 바로 그 연결입니다. 같은 시점에 안내 문구와 data-state도 갱신해야 하므로, 이 작업들을 하나의 함수에 모읍니다. 이 예제에서는 그 함수에 render라는 이름을 붙였습니다. “현재 상태를 DOM으로 표현한다”는 역할을 드러내기 위한 이름입니다.

render를 정의하는 것만으로 실행되지는 않습니다. 처음 화면을 맞출 때 한 번 호출하고, 상태를 변경한 뒤 다시 호출합니다. 값을 바꾸는 코드와 화면에 반영하는 코드를 순서대로 실행하는 함수가 setChecked입니다. 이 함수는 새 값을 받아 state를 갱신하고 render를 호출합니다. 상태를 바꾸는 모든 경로가 여기를 지나도록 하면 표시 갱신을 빠뜨릴 가능성이 줄어듭니다.

입력은 들어오고, 표시 값은 한 방향으로 나갑니다

사용자가 체크박스를 조작하면 브라우저가 먼저 input.checked를 바꾸고 change 이벤트를 알립니다. 리스너는 실제 변경 결과를 읽어 setChecked에 전달합니다. “코드로 켜기” 버튼은 사용자의 체크박스 조작을 흉내 내지 않고 같은 함수에 true를 전달합니다. 출발점은 달라도 이후의 상태 변경과 화면 반영 과정은 같습니다.

이 구조의 흐름은 입력 또는 명령 → 상태 변경 → 파생값 계산 → DOM 반영입니다. 표시할 값을 여러 곳에서 각자 결정하지 않고 기준 상태에서 화면 쪽으로 전달하므로 단방향 갱신이라고 설명할 수 있습니다. 사용자 입력은 DOM에서 읽어 들어올 수 있지만, 최종 표시를 결정하는 방향은 기준 상태에서 각 표시 요소로 향합니다.

change를 받을 때는 무조건 이전 state의 반대로 뒤집는 대신 input.checked를 읽습니다. 브라우저가 이미 바꾼 결과를 받아들이는 것이기 때문입니다. 별도의 “반대로 바꾸기” 버튼을 만든다면 그때는 state를 기준으로 다음 값을 계산할 수 있습니다. 발생한 결과를 받아들이는 일과 새로운 변경을 명령하는 일을 구분해야 합니다.

변경 함수와 표시 함수를 한 줄씩 읽기

아래 코드는 문서에서 input과 summary 요소를 이미 찾았다고 가정합니다. 값 저장과 DOM 반영이라는 두 책임을 최소한의 문장으로 표현했습니다.

let checked = false;
function render() {
  input.checked = checked;
  summary.textContent = checked ? "켜짐" : "꺼짐";
}
function setChecked(next) {
  checked = next;
  render();
}
render();
  1. 첫 줄은 알림의 현재 상태를 false로 정합니다. 이 변수는 자바스크립트의 값이며 아직 체크박스에 쓰지 않았습니다.
  2. render의 첫 대입문은 상태를 입력 요소의 현재 선택 값에 씁니다. 둘째 대입문은 같은 상태에서 문구를 계산해 텍스트로 씁니다.
  3. setChecked의 매개변수 next는 새로 결정할 값을 받습니다. checked에 그 값을 저장한 뒤 render를 호출하므로 데이터 변경 다음에 표시 갱신이 이어집니다.
  4. 마지막 render 호출은 처음 화면을 맞춥니다. 함수 정의가 두 개 있다는 사실만으로 초기 표시가 준비되지는 않기 때문에 명시적으로 호출합니다.

예제 화면의 실제 코드는 checked 하나 대신 state 객체를 사용하고 data-state와 JSON 표시도 함께 갱신합니다. 원리는 같습니다. render를 updateView로 이름만 바꾸어도 모든 호출 위치를 함께 고치면 같은 동작을 합니다. 브라우저가 제공하는 특별한 상태 감지 명령이 아니라 우리가 만든 함수이기 때문입니다.

값의 변경, 이벤트, 화면 그리기를 구분하기

프로그램에서 input.checked를 대입해도 change 이벤트는 자동 발생하지 않습니다. 따라서 render 안에서 체크 값을 쓰는 것이 다시 change를 만들고, 그 change가 setChecked를 호출하는 반복으로 이어지지는 않습니다. 프로그램 변경은 필요한 변경 함수를 직접 호출하면 됩니다. DOM 속성을 바꾸는 것과 이벤트를 전달하는 것은 서로 다른 동작입니다.

반대로 render 호출을 빼면 사용자 조작으로 체크 표시만 바뀌는 상황이 생깁니다. 브라우저의 기본 동작은 남아 있기 때문입니다. 이벤트 리스너가 메모리의 state를 갱신해도 안내 문구나 JSON은 마지막으로 기록한 텍스트를 유지합니다. 화면의 JSON 문자열은 객체 자체가 아니라 객체를 읽어 만든 표시라는 점에서 역시 파생값입니다.

실행 예제의 render 횟수는 이 함수가 몇 번 호출되었는지 세는 학습용 값입니다. 브라우저가 실제로 화면을 몇 번 그렸는지 나타내지는 않습니다. 같은 상태를 다시 설정해도 현재 코드에서는 render가 다시 호출됩니다. 표시 내용은 그대로인데 횟수가 증가할 수 있는 이유입니다. 함수 실행과 브라우저의 렌더링 과정을 같은 사건으로 보면 이 차이를 설명하기 어렵습니다.

값을 소유한다는 것과 외부에서 제어한다는 것

상태를 소유한다는 말은 그 값을 어디에 저장하며 누가 최종 변경을 결정하는지를 뜻합니다. 지금은 예제의 setChecked가 내부 state를 직접 바꿉니다. 하지만 여러 설정을 한 번에 저장하는 화면이라면 바깥의 설정 객체가 전체 값을 소유하고, 각 입력은 그 값을 보여주는 역할만 맡을 수도 있습니다.

이때 입력은 “true로 바꾸고 싶다”는 요청을 바깥 코드에 알립니다. 바깥 코드는 요청을 받아 자신의 값을 갱신하거나, 조건에 따라 기존 값을 유지한 뒤 최종 값을 다시 입력에 전달합니다. 이런 관계를 외부 제어라고 이해할 수 있습니다. 어떤 프레임워크의 전용 기능이 아니라, 값을 결정하는 주체와 값을 표시하는 주체 사이에 세운 약속입니다.

내부와 외부 양쪽에서 같은 상태를 독립적으로 결정하면 어느 쪽이 맞는지 충돌할 수 있습니다. 재사용 가능한 구성으로 발전시킬 때는 현재 값이 들어오는 통로와 변경 요청이 나가는 통로를 먼저 정해야 합니다. 이 장의 변경 함수와 표시 함수를 분리한 경험은 그 통로를 구분하는 출발점이 됩니다.

연결의 단계를 나누어 확인하기

먼저 자동 연결이 없다는 사실을 확인하고, 하나의 값에서 여러 표현을 계산한 뒤, 두 작업을 하나의 변경 함수로 연결합니다. 세 예제는 서로 다른 데이터를 사용합니다.

예제 6-1 · 두 객체의 값은 자동으로 연결되지 않음

메모리의 값만 바꾸면 화면은 어떨까요?

예상하기: state.checked를 true로 바꾸면 아래 “화면의 알림” 문구도 바로 켜짐이 될까요?

const state = { checked: false };
state.checked = true; // 메모리만 변경
// 아래 줄을 실행해야 표시가 바뀝니다.
view.textContent = state.checked ? "켜짐" : "꺼짐";

화면의 알림: 꺼짐

메모리 checked: false · 마지막으로 쓴 화면: 꺼짐

확인할 결과: 1번만 누르면 메모리는 true지만 화면의 알림은 꺼짐입니다. 2번을 눌러야 켜짐으로 바뀝니다. 아래 관찰 문구는 현재 값을 읽어 알려주는 실험 도구이며, 실제 알림 표시는 #manual-view입니다.

예제 6-3 · 입력 → 상태 변경 → DOM 반영

입력 경로가 달라도 같은 상태 변경

예상하기: 체크박스를 직접 바꾸는 경우와 코드로 켜기 버튼을 누르는 경우가 같은 화면을 만들려면 어떤 처리를 공유해야 할까요?

function setChecked(checked) {
  state = { checked };
  render();
}
input.addEventListener("change", (event) => {
  setChecked(event.currentTarget.checked);
});

알림: 

render 호출: 0회


확인할 결과: 어느 입력 경로든 체크 표시, 문구, JSON이 함께 바뀝니다. 이미 켜진 상태에서 다시 코드로 켜기를 눌러도 render 호출은 증가합니다. 이 수는 함수 호출 횟수이며 브라우저의 실제 paint 횟수가 아닙니다. 초기화하면 초기 render 1회부터 다시 셉니다.
