이벤트는 어떻게
코드에 도착할까요?

이벤트는 발생한 일을 코드에 알려주는 방식입니다. 이벤트를 받는 함수를 등록하는 일부터, 그 함수가 호출되는 시점과 문서 안의 전달 경로까지 차례로 이해합니다.

이벤트를 읽는 네 가지 기준

  • 등록할 때와 실제 핸들러가 호출될 때를 구분합니다.
  • 이벤트의 대상과 현재 리스너의 위치를 구분합니다.
  • 이벤트 전파, 기본 동작, 프로그램의 값 대입을 따로 설명합니다.
  • 키보드·포인터·한글 입력이 이벤트 객체에 남기는 정보를 읽고, 처리한 키의 기본 동작만 취소합니다.

이벤트는 발생한 사실을 전달하는 객체입니다

사용자가 버튼을 누르거나 입력창의 내용을 바꾸면 브라우저는 그 일을 자바스크립트 코드에 알려줄 수 있습니다. 이렇게 “무언가 발생했다”는 사실을 전달하는 체계가 이벤트입니다. 이벤트 자체가 화면을 바꾸는 함수는 아닙니다. 무엇이 일어났는지를 전달하면, 그 사실을 받은 코드가 필요한 일을 결정합니다.

코드가 받는 것은 이벤트 객체입니다. 객체에는 발생한 일의 종류를 나타내는 type, 대상인 target 등의 정보가 들어 있습니다. 키보드 이벤트라면 어떤 키인지, 포인터 이벤트라면 좌표가 무엇인지처럼 종류에 맞는 정보도 포함됩니다. 따라서 “클릭했다”는 사실과 “클릭했으니 문구를 바꾼다”는 처리는 서로 분리됩니다.

특정 대상에 특정 종류의 이벤트를 받겠다고 연결하는 것을 리스너 등록이라고 합니다. 등록된 뒤 실제 처리를 담당하는 함수는 이벤트 핸들러라고 부릅니다. 실무에서는 리스너라는 말로 이 함수까지 가리키기도 합니다. 중요한 것은 등록 정보와 실행할 함수가 연결된다는 점입니다.

이 함수는 우리가 그 자리에서 호출하지 않고 다른 코드에 전달해 둡니다. 전달받은 쪽이 정해진 조건에 호출하는 함수를 콜백이라고 합니다. 이벤트 핸들러는 콜백의 한 사례입니다. “콜백”은 함수의 문법이나 비동기 실행을 뜻하지 않고, 누가 그 함수를 호출하는지에 관한 말입니다.

발생 사실과 처리 방법을 분리하는 이유

코드를 위에서 아래로 한 번 실행하는 것만으로는 사용자가 나중에 무엇을 누를지 알 수 없습니다. 입력창 값을 계속 반복해서 확인하는 것도 불필요한 일을 늘립니다. 대신 브라우저에 관심 있는 일을 등록해 두면, 그 일이 발생한 순간 필요한 함수를 실행할 수 있습니다. 문서를 준비하는 코드와 사용자 행동에 반응하는 코드가 이 지점에서 연결됩니다.

같은 동작은 여러 입력 방식에서 시작될 수도 있습니다. 폼 제출은 제출 버튼으로 시작할 수도 있고 입력창의 Enter 키에서 시작할 수도 있습니다. “어떤 마우스 버튼을 눌렀는가” 대신 “폼을 제출하려 한다”는 이벤트를 처리하면, 입력 수단마다 같은 로직을 중복해서 작성할 필요가 줄어듭니다. 이벤트를 고르는 일은 우리가 어떤 의미의 행동을 처리하려는지 정하는 일이기도 합니다.

등록, 호출, 전달 경로는 서로 다른 단계입니다

등록할 때는 함수를 전달합니다

button.addEventListener("click", handleClick)은 버튼의 click 이벤트와 handleClick 함수를 연결합니다. 함수 이름 뒤에 괄호가 없으므로 여기서 함수 본문을 실행하지 않습니다. handleClick()이라고 쓰면 지금 함수를 호출하고, 그 반환값을 addEventListener에 넘기게 됩니다. 함수 객체를 전달하는 표현과 함수 호출 표현의 차이가 실행 시점을 결정합니다.

나중에 이벤트가 전달되면 브라우저가 핸들러를 호출하면서 이벤트 객체를 인수로 줍니다. 핸들러의 매개변수 이름을 event라고 정했다면 그 안에서 event.target을 읽을 수 있습니다. event라는 전역 변수가 자동으로 만들어진다고 이해해서는 안 됩니다. 매개변수를 통해 받은 값을 읽는 것입니다.

브라우저의 사용자 입력과 코드의 직접 전달

사용자의 클릭을 처리하는 일은 일반적으로 현재 실행 중인 자바스크립트 작업이 끝난 뒤 브라우저가 다음 작업으로 진행합니다. 하지만 이벤트 핸들러가 언제나 나중에 호출되는 것은 아닙니다. 코드에서 dispatchEvent를 호출하면 그 호출 안에서 관련 핸들러가 실행되고, 처리가 끝나야 다음 줄로 넘어갑니다. 이런 실행을 동기 실행이라고 합니다.

예를 들어 “준비됨”이라는 자체 이벤트를 만들고 전달할 수도 있습니다. 직접 전달한 이벤트는 사용자가 실제로 조작했다는 사실과 같지 않으며, 일반적으로 사용자 입력의 모든 기본 동작을 재현하지도 않습니다. 이벤트를 전달하는 기능과 입력 장치를 흉내 내는 기능을 같은 것으로 생각하지 않는 것이 좋습니다.

문서 안에서 내려갔다 올라오는 경로

버튼 안의 span에서 클릭이 시작되면 이벤트는 해당 요소만의 일이 아닙니다. 대상의 조상에서 대상 쪽으로 내려가는 캡처 단계, 대상 자체에서 처리하는 단계, 조상 쪽으로 올라가는 버블 단계로 전달될 수 있습니다. 부모에 기본 방식으로 등록한 click 리스너는 버블 단계에서 호출됩니다. 캡처 시점에 받으려면 등록할 때 capture 옵션을 true로 지정합니다.

이 예에서 target은 이벤트의 출발 대상인 span이고, currentTarget은 지금 실행하는 핸들러가 등록된 요소입니다. 같은 이벤트라도 버튼 핸들러에서는 currentTarget이 버튼, 부모 핸들러에서는 부모입니다. 모든 이벤트가 버블링하는 것은 아니므로 이 경로는 이벤트 종류의 특성과 함께 이해해야 합니다.

리스너를 등록할 때 정할 수 있는 것

addEventListener의 세 번째 인수로 옵션 객체를 전달할 수 있습니다. capture는 앞에서 본 캡처 단계 등록입니다. once: true로 등록한 리스너는 한 번 호출된 뒤 자동으로 제거됩니다. signal은 여러 리스너를 한 번에 제거하는 방법으로 11장에서 다룹니다.

passive: true는 “이 리스너는 preventDefault를 호출하지 않겠다”는 약속입니다. 왜 이런 약속이 필요할까요? 마우스 휠을 굴리거나 화면을 손가락으로 밀면 wheel이나 touchmove 이벤트가 발생하고, 리스너는 preventDefault로 스크롤을 막을 수 있습니다. 그래서 브라우저는 리스너 실행이 끝날 때까지 스크롤을 미뤄야 하고, 리스너가 오래 걸리면 화면이 늦게 움직입니다. passive 약속이 있으면 브라우저는 기다리지 않고 바로 스크롤합니다.

같은 이유로 브라우저는 window, document, body에 등록한 touchstart, touchmove, wheel 리스너를 따로 지정하지 않아도 passive로 취급합니다. 그 안에서 preventDefault를 호출하면 무시되고 콘솔에 경고가 남습니다. 스크롤을 정말 막아야 한다면 { passive: false }를 명시합니다.

직접 만든 이벤트는 기본적으로 버블링하지 않습니다

new Event("notice")로 만든 이벤트는 bubbles와 cancelable이 모두 false입니다. 대상 요소의 리스너만 받고 부모에는 전달되지 않으며, 리스너가 preventDefault를 호출해도 효과가 없습니다. 부모까지 알리려면 new Event("notice", { bubbles: true })처럼 만들 때 정합니다. 함께 전달할 데이터가 있다면 new CustomEvent("notice", { detail: { value: 3 } })로 만들고 리스너에서 event.detail로 읽습니다.

취소할 수 있는 이벤트, 즉 cancelable을 true로 만든 이벤트를 전달하면, 리스너 중 하나라도 preventDefault를 호출했을 때 dispatchEvent가 false를 돌려줍니다. 이벤트를 보낸 코드는 이 값을 보고 원래 하려던 일을 계속할지 정할 수 있습니다. 브라우저의 기본 동작과 같은 약속을 직접 만든 기능에 적용하는 방법입니다. 코드로 전달한 이벤트는 isTrusted가 false여서 사용자의 실제 입력과 구분됩니다.

작은 코드에서 호출 시점 읽기

아래는 이미 찾은 button 요소에 notice라는 자체 이벤트를 연결하는 짧은 코드입니다. notice는 예제를 위해 정한 이름이며 버튼의 기본 동작과는 관계가 없습니다.

function handleNotice(event) {
  console.log("B", event.type);
}
button.addEventListener("notice", handleNotice);
console.log("A");
button.dispatchEvent(new Event("notice"));
console.log("C");
  1. function handleNotice(event)는 함수를 정의합니다. 아직 로그를 출력하지 않으며, 나중에 받은 객체를 event라는 이름으로 읽도록 준비합니다.
  2. 함수 안의 console.log는 호출될 때만 실행됩니다. 여기서는 B와 이벤트 종류를 출력하는 처리입니다.
  3. addEventListener는 함수 자체를 등록합니다. 함수 정의와 등록만 끝난 시점에도 B는 출력되지 않습니다.
  4. 첫 console.log가 A를 출력합니다. 그다음 new Event는 notice라는 종류의 객체를 만들고 dispatchEvent가 버튼에 전달합니다.
  5. 전달 도중 핸들러가 호출되어 B와 notice가 출력됩니다. dispatchEvent가 반환한 뒤 마지막 줄이 C를 출력하므로 순서는 A → B → C입니다.

연결이 필요 없어지면 같은 요소에서 같은 종류와 함수로 removeEventListener("notice", handleNotice)를 호출합니다. 본문이 같은 새 함수를 만들면 다른 함수 객체이므로 기존 연결을 지우지 못합니다. 캡처로 등록했다면 해제할 때도 같은 capture 값을 사용해야 합니다.

이벤트 전달과 기본 동작을 구분하기

브라우저는 요소에 따라 기본 동작을 제공합니다. 링크의 이동, 폼 제출, 체크박스의 선택 변경 등이 그 예입니다. 이벤트를 받아 실행하는 우리 코드와 이러한 기본 동작은 별개의 부분입니다. 취소 가능한 기본 동작을 막는 preventDefault는 이벤트가 부모에 전달되는 것을 막지 않습니다.

반대로 stopPropagation은 다음 요소로 이벤트가 전파되는 것을 멈춥니다. 폼의 submit 전파를 멈추어도 그 자체로 기본 제출을 취소하지는 않습니다. 이미 실행된 조상의 캡처 핸들러를 되돌리지도 않습니다. “부모가 알지 못하게 한다”와 “브라우저가 원래 하려던 일을 하지 않게 한다”를 구분하면 두 메서드의 역할이 분명해집니다.

input, change, submit도 서로 다른 사실을 전달합니다. 텍스트 입력의 input은 사용자 편집으로 값이 바뀌는 동안 발생합니다. change는 값의 변경이 확정될 때 발생하며, 텍스트 입력에서는 값을 바꾼 뒤 포커스를 옮길 때 관찰할 수 있습니다. 체크박스의 change는 선택을 바꾸는 순간 발생합니다. submit은 개별 입력의 변화가 아니라 폼 제출의 시도를 뜻합니다.

프로그램에서 value나 checked만 대입하면 input이나 change가 자동으로 발생하지 않습니다. 값이 바뀌었다는 사실과 특정 이벤트가 발생했다는 사실은 같은 조건이 아니기 때문입니다. 화면을 갱신할 목적이라면 필요한 함수를 직접 호출할 수 있으며, 이벤트를 일부러 만들어 보내야 하는 것은 아닙니다.

입력 장치마다 이벤트 객체가 알려주는 정보가 다릅니다

키보드 이벤트는 키의 의미와 위치를 따로 알려줍니다

keydown 이벤트 객체의 key는 눌린 키가 지금 무엇을 뜻하는지 나타냅니다. 같은 물리 키라도 Shift를 함께 누르면 "a"가 "A"가 되고, 키보드 배열이나 입력 언어가 바뀌면 다른 값이 됩니다. code는 의미와 관계없이 눌린 물리 키의 위치를 나타냅니다. 배열이 달라도 같은 자리의 키는 같은 code를 가집니다. 숫자로 된 keyCode는 더 이상 권장되지 않는 속성이므로 어떤 키인지 판단하는 데 사용하지 않습니다. 뒤에서 볼 한글 조합 확인이 거의 유일한 예외입니다.

조작의 의미를 판단할 때는 key를 사용합니다. “다음 항목으로 이동”은 화살표가 뜻하는 방향이고, “a로 시작하는 항목 찾기”는 입력한 글자의 의미이기 때문입니다. code는 게임의 이동 키처럼 위치 자체가 중요한 경우에 사용합니다. Space 키의 key는 "Space"라는 단어가 아니라 공백 문자 " "라는 점도 기억해 둡니다. 키를 길게 누르고 있으면 keydown이 반복해서 발생하며, 반복된 이벤트의 repeat는 true입니다.

처리한 키의 기본 동작만 취소합니다

키에도 브라우저의 기본 동작이 있습니다. 스크롤할 수 있는 영역에서 방향키와 Space는 내용을 움직이고, Home과 End는 처음과 끝으로 이동합니다. Tab은 다음 포커스 대상으로 이동하고, 폼 안의 입력에서 누른 Enter는 제출을 시도합니다. keydown 핸들러에서 preventDefault를 호출하면 그 키의 기본 동작이 일어나지 않습니다.

그래서 직접 처리하기로 한 키만 취소합니다. 목록에서 방향키로 강조 항목을 옮긴다면 방향키의 스크롤만 막고, 처리하지 않는 Tab과 글자 키는 그대로 둡니다. 핸들러 첫 줄에서 모든 키를 막으면 입력창에 글자가 들어가지 않거나 키보드 사용자가 그 영역을 빠져나가지 못합니다. Tab 이동을 막는 일은 대화 상자 안에서 포커스를 순환시키는 것처럼 대신할 이동 규칙을 직접 제공하는 경우로 한정합니다.

포인터의 누름과 뗌은 별개의 이벤트입니다

마우스로 한 번 클릭하는 동안에도 여러 이벤트가 이어집니다. 일반적인 순서는 pointerdown, mousedown, 포커스 이동, pointerup, mouseup, click입니다. 포커스 이동은 mousedown의 기본 동작이고, click은 누름과 뗌이 같은 요소에서 끝났을 때 생기는 결과입니다. 한 버튼에서 누르고 다른 버튼 위에서 떼면 두 버튼 모두 click을 받지 않습니다.

그래서 “누르는 순간”에 반응해야 하는 일에는 pointerdown을 사용합니다. 열린 메뉴의 바깥을 누르자마자 메뉴를 닫는 동작이 그런 예입니다. 반대로 “실행”을 뜻하는 동작에는 click을 사용합니다. 키보드로 버튼을 활성화해도 click이 발생하기 때문입니다. 키보드나 코드에서 발생한 click은 detail이 0이고, 포인터로 누른 click에는 연속으로 누른 횟수가 들어갑니다.

한글은 조합이 끝나야 글자가 확정됩니다

한글은 여러 키를 눌러 한 글자를 만듭니다. ㄱ과 ㅏ를 입력하면 입력기(IME)가 “가”를 조합하고, 다음 글자나 Enter를 입력하면 그 글자가 확정됩니다. 조합하는 동안 브라우저는 compositionstart, compositionupdate, compositionend 이벤트를 보내고, 그 사이에 발생한 keydown의 isComposing은 true입니다. 일부 브라우저는 조합 중인 keydown의 key를 "Process"로, keyCode를 229로 보고합니다.

Enter를 “제출”로 처리하는 keydown 핸들러가 조합 상태를 확인하지 않으면, 글자를 확정하려고 누른 Enter까지 제출로 처리할 수 있습니다. 영어로 입력할 때는 드러나지 않는 문제입니다. 조합을 끝내는 Enter의 isComposing 값을 브라우저마다 다르게 보고하는 경우가 있어서, isComposing과 keyCode 229를 함께 확인하는 방법이 널리 쓰입니다. 입력된 값 자체를 다룰 때는 keydown보다 input 이벤트가 적합합니다.

이벤트의 질문을 하나씩 따로 실험하기

언제 호출되는가, 어디로 전달되는가, 기본 동작을 취소하는가, 어떤 변화가 이벤트를 만드는가를 나눠서 봅니다. 뒤의 네 예제는 키의 의미와 위치, 키의 기본 동작, 포인터의 누름과 뗌, 한글 조합을 차례로 봅니다. 마지막 예제는 코드가 직접 만든 이벤트가 어디까지 전달되는지 봅니다. 한 예제의 조작은 다른 예제의 기록을 바꾸지 않습니다.

예제 4-1 · 등록과 실행 시점

dispatchEvent 뒤의 코드는 언제 실행될까요?

예상하기A, B, C 중 무엇이 먼저 기록될까요? “이벤트는 항상 나중에 실행된다”는 설명으로 맞힐 수 있을까요?

button.addEventListener("notice", () => log("B"));
log("A");
button.dispatchEvent(new Event("notice"));
log("C");

아직 전달하지 않았습니다.

확인할 결과A → B → C입니다. 등록만으로 B가 실행되지는 않지만 dispatchEvent가 호출되면 핸들러 실행을 마친 뒤 다음 줄로 갑니다. 버튼을 누를 때마다 로그를 새로 만듭니다.

예제 4-2 · 전달 경로와 대상

하나의 클릭을 세 위치에서 읽기

예상하기안쪽 글자를 누르면 target도 리스너 위치마다 바뀔까요? 전파를 멈추면 부모의 캡처 기록도 사라질까요?

parent.addEventListener("click", log, { capture: true });
button.addEventListener("click", log);
parent.addEventListener("click", log);

마우스로 안쪽 글자를 눌러본 다음, Tab으로 버튼에 이동해 Enter나 Space로도 실행해보세요.

아직 클릭하지 않았습니다.

확인할 결과부모 캡처 → 버튼 → 부모 버블 순서입니다. 글자를 직접 누르면 target은 계속 span이고 currentTarget은 리스너가 연결된 요소를 가리킵니다. 키보드로 버튼을 활성화하면 target은 버튼입니다. 전파를 멈추면 마지막 부모 버블 기록만 없어집니다. 매 클릭의 로그를 새로 표시합니다.

예제 4-3 · 기본 동작과 전파의 차이

제출을 취소해도 부모가 알 수 있을까요?

예상하기preventDefault를 호출하면 submit이 부모에게도 전달되지 않을까요?

form.addEventListener("submit", (event) => {
  event.preventDefault();
  show(input.value);
});

아직 제출하지 않았습니다.

확인할 결과페이지는 이동하지 않지만 부모의 submit 횟수는 증가합니다. 문구 입력창에서 Enter를 눌러도 같은 처리가 실행됩니다. submit을 처리하면 입력 수단마다 로직을 반복하지 않아도 됩니다.

예제 4-4 · 값 변경과 이벤트 발생

입력 중, 입력 확정, 코드 대입 비교

예상하기한 글자를 입력한 순간과 Tab으로 나간 순간은 같은 이벤트일까요? 코드로 value를 바꾸면 어떤 이벤트가 생길까요?

input.addEventListener("input", record);
input.addEventListener("change", record);
input.value = "코드에서 넣은 값"; // 이벤트를 보내지는 않음

input: 0회 · change: 0회

아직 코드로 대입하지 않았습니다.

확인할 결과직접 편집하는 동안 input이 발생하고, 값을 바꾼 뒤 포커스를 옮기면 change가 발생합니다. 코드 대입 자체는 둘 다 발생시키지 않습니다. 다만 입력을 마치고 버튼으로 이동할 때 생긴 change와 버튼의 대입은 별개입니다. 한글 입력은 조합 과정에 따라 input 횟수가 다를 수 있습니다.

예제 4-5 · 키의 의미와 위치

Space 키의 key 값은 무엇일까요?

예상하기Space, Shift+A, 아래 방향키를 차례로 누르면 key와 code는 각각 어떻게 기록될까요? 한글 입력으로 바꾼 뒤 같은 A 자리를 누르면 둘 중 무엇이 바뀔까요?

field.addEventListener("keydown", (event) => {
  show(event.key, event.code, event.repeat);
});

아직 누른 키가 없습니다.

확인할 결과Space의 key는 공백 문자라서 기록에 key: " "로 표시되고, code는 "Space"입니다. Shift+A의 key는 "A", code는 "KeyA"입니다. 한글 입력에서 같은 자리를 누르면 code는 그대로 "KeyA"이고 key는 "ㅁ"이나 "Process"처럼 달라집니다. 키를 길게 누르면 repeat가 true인 기록이 이어집니다. 최근 8개만 표시합니다.

예제 4-6 · 키의 기본 동작

방향키의 기본 동작을 취소하면 무엇이 사라질까요?

예상하기목록 영역에 Tab으로 들어가 아래 방향키를 누르면 무엇이 움직일까요? 방향키를 직접 처리하도록 바꾼 뒤에도 Tab으로 영역을 빠져나갈 수 있을까요?

const handledKeys = ["ArrowDown", "ArrowUp", "Home", "End"];

예제 4-7 · 누름과 뗌

누른 버튼과 뗀 버튼이 다르면 click은 누가 받을까요?

예상하기버튼 A를 한 번 클릭하면 몇 줄이 기록될까요? A에서 누른 채로 B 위로 옮겨 떼면 A와 B 중 누가 click을 받을까요?

const types = ["pointerdown", "mousedown", "focus", "pointerup", "mouseup", "click"];
for (const type of types) {
  buttonA.addEventListener(type, record);
  buttonB.addEventListener(type, record);
}

아직 누르지 않았습니다.

확인할 결과A를 클릭하면 pointerdown, mousedown, focus, pointerup, mouseup, click 순서로 기록됩니다. A에서 누르고 B에서 떼면 누름 기록은 A에, 뗌 기록은 B에 남고 두 버튼 모두 click이 없습니다. 이때 두 버튼을 감싼 영역이 click을 받는지는 브라우저에 따라 다를 수 있습니다. Tab으로 A에 이동해 Enter를 누르면 click 한 줄만 기록되고 detail은 0입니다. macOS의 일부 브라우저는 버튼을 클릭해도 포커스를 옮기지 않으므로 focus 기록이 없을 수 있고, 터치에서는 mousedown과 mouseup이 pointerup 뒤에 이어질 수 있습니다. 새로 누를 때마다 기록을 새로 시작합니다.

예제 4-8 · 한글 조합과 Enter

글자를 확정하려고 누른 Enter도 제출일까요?

예상하기한글로 “가”를 입력한 직후 Enter를 한 번 누르면, 조합을 확인하지 않는 처리와 확인하는 처리는 각각 몇 번 실행될까요?

field.addEventListener("keydown", (event) => {
  if (event.key !== "Enter") return;
  plainCount += 1;                                   // 조합 상태를 보지 않는 처리
  if (event.isComposing || event.keyCode === 229) return;
  guardedCount += 1;                                 // 조합이 끝난 Enter만 처리
});

조합을 확인하지 않는 처리: 0회 · 조합을 확인하는 처리: 0회

아직 입력하지 않았습니다.

확인할 결과기록에서 compositionstart와 compositionend 사이의 keydown은 isComposing이 true이거나 keyCode가 229입니다. 조합을 확인하지 않는 처리는 글자를 확정하는 Enter까지 셀 수 있으므로 확인하는 처리보다 크거나 같습니다. 정확한 횟수는 브라우저와 입력기에 따라 다르므로 기록에서 각 Enter의 isComposing과 keyCode를 비교하세요. 영어로 입력하면 두 횟수가 같습니다. 최근 10개만 표시합니다.

예제 4-9 · 직접 만든 이벤트의 전달 범위

직접 만든 이벤트는 부모까지 올라갈까요?

예상하기bubbles 없이 만든 이벤트를 안쪽 요소에 전달하면 부모의 리스너가 실행될까요? 부모가 preventDefault를 호출하면 dispatchEvent는 무엇을 돌려줄까요?

const event = new CustomEvent("choose", {
  bubbles, cancelable: true, detail: { value: "A" },
});
const proceed = inner.dispatchEvent(event);
// proceed가 false면 리스너 중 누군가 취소했습니다.

안쪽 요소

아직 전달하지 않았습니다.

확인할 결과bubbles를 끄면 안쪽 리스너만 실행되고 dispatchEvent는 true입니다. 켜면 부모 리스너도 같은 detail.value를 읽습니다. 버블링을 켠 상태에서 부모가 취소하면 dispatchEvent가 false를 돌려주고, 보낸 쪽이 “기본 처리를 건너뜀”으로 기록합니다. 버블링을 끈 상태에서는 부모의 취소 설정이 아무 효과도 없습니다. isTrusted는 항상 false입니다.
