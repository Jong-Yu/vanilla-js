8장 · 폼과 포커스의 기본 계약

HTML 요소가 제공하는
입력과 이동의 규칙

폼 요소는 화면에 그려진 모양 이상의 기능을 갖습니다. 브라우저가 제공하는 의미, 키보드 조작, 포커스, 데이터 수집 규칙을 이해하면 직접 구현할 동작의 경계가 보입니다.

네이티브 요소의 의미포커스와 이동 순서폼 데이터의 구성현재 값과 기본값키보드와 접근성입력 검증동작 예제

네이티브 요소는 브라우저가 제공하는 동작의 묶음입니다

네이티브 HTML 요소는 button, input, form처럼 브라우저가 의미와 기본 동작을 알고 있는 요소입니다. button을 사용하면 단지 버튼 모양의 영역이 생기는 데 그치지 않습니다. 브라우저는 그것이 활성화할 수 있는 조작임을 알고, 지원하는 키보드 입력으로 클릭을 발생시키며, 접근성 정보를 통해 보조 기술에도 그 역할을 전달합니다.

반대로 일반 div에 클릭 리스너를 달면 마우스 클릭에는 반응할 수 있지만, 그 요소가 자동으로 키보드 조작 가능한 버튼이 되는 것은 아닙니다. 포커스 가능 여부, 키보드 활성화, 비활성 상태의 처리 등을 별도로 고려해야 합니다. 따라서 입력과 조작을 만들 때는 필요한 기능을 이미 갖춘 요소를 출발점으로 삼는 것이 유리합니다.

이 기본 동작을 일종의 브라우저 계약으로 볼 수 있습니다. 개발자가 올바른 요소와 속성을 선언하면 브라우저가 정해진 규칙을 수행합니다. checkbox의 레이블을 클릭하면 선택이 바뀌고, submit 버튼은 자신이 속한 폼의 제출을 시도합니다. JavaScript가 맡을 일은 이 계약에 없는 추가 동작을 연결하거나, 필요한 경우 기본 동작을 명시적으로 취소하는 것입니다.

포커스는 키보드 입력을 받을 위치입니다

포커스(focus)는 현재 키보드 입력을 받을 요소가 어디인지 나타내는 브라우저 상태입니다. 입력창에 포커스가 있으면 글자를 입력할 수 있고, 버튼에 포커스가 있으면 해당 버튼을 키보드로 활성화할 수 있습니다. 마우스가 올라간 위치와 포커스는 다를 수 있습니다.

선택(selection)도 포커스와 다릅니다. 텍스트 입력에서는 한 입력창이 포커스를 가진 상태에서 그 안의 일부 글자를 선택할 수 있습니다. 선택된 탭을 표시하는 데이터 역시 별도의 컴포넌트 상태입니다. 어떤 탭에 포커스가 있다고 해서 그 탭의 패널을 반드시 즉시 선택해야 하는 것은 아닙니다. 포커스의 위치와 제품이 표현하는 선택 상태를 한 값으로 취급하면 키보드 동작을 설계하기 어려워집니다.

현재 문서에서 포커스를 가진 요소는 document.activeElement로 읽습니다. 다른 프레임이나 Shadow DOM이 관여하면 어느 문서의 activeElement를 읽는지도 중요합니다. 이 교재를 한 파일 화면에서 읽는 경우, 예제 안의 document는 실습 프레임의 문서를 뜻합니다.

const input = document.querySelector("#nickname");
input.focus();
console.log(document.activeElement === input);
  1. 첫 줄은 이름 입력 요소를 찾아 변수에 보관합니다. 이 단계는 요소를 찾을 뿐 포커스를 이동하지 않습니다.
  2. 둘째 줄은 그 요소로 포커스 이동을 요청합니다. 대상이 포커스를 받을 수 있는 상태여야 실제로 이동합니다.
  3. 셋째 줄은 문서의 현재 포커스 요소와 찾은 입력이 같은 객체인지 비교합니다. 이 예제의 활성 입력에서는 true가 됩니다.

순차 포커스 이동은 Tab이나 Shift+Tab으로 문서 안의 대상을 차례로 이동하는 방식입니다. focus()로 특정 대상을 지정하는 프로그램 이동과는 구분됩니다. tabindex="0"은 일반적인 문서 순서의 Tab 이동에 포함하고, tabindex="-1"은 Tab 순서에는 추가하지 않으면서 프로그램으로 포커스를 줄 수 있게 합니다.

예를 들어 새 화면의 제목은 사용자가 Tab을 누를 때마다 들를 조작 대상은 아니지만, 화면이 바뀌었음을 알리려고 한 번 포커스를 옮길 수 있습니다. 이런 경우 제목에 -1을 사용합니다. 양수 tabindex로 순서를 강제로 재배열하기보다 문서 자체의 순서를 자연스럽게 구성하세요. 기본적인 순차 이동에는 브라우저와 운영체제의 키보드 탐색 설정도 영향을 줍니다.

포커스가 옮겨갈 때는 이벤트가 발생합니다. 포커스를 잃는 요소에서 blur와 focusout이, 포커스를 받는 요소에서 focus와 focusin이 발생합니다. 두 쌍의 차이는 버블링입니다. focus와 blur는 버블링하지 않으므로 부모에 등록하면 자식의 포커스 변화를 받을 수 없습니다. focusin과 focusout은 버블링하므로 영역이나 document 한 곳에서 “안으로 들어왔다”와 “밖으로 나갔다”를 들을 수 있습니다.

이 이벤트 객체의 relatedTarget은 이동의 상대편 요소입니다. focusout에서는 포커스가 갈 요소, focusin에서는 포커스가 떠난 요소를 가리킵니다. 포커스를 받을 수 없는 빈 곳을 클릭하거나 다른 창으로 이동하면 갈 곳이 없으므로 null입니다. 포커스가 영역 밖으로 나갔는지는 relatedTarget이 영역 안에 있는지로 판단하고, null인 경우를 어떻게 처리할지는 기능의 목적에 맞춰 따로 정합니다.

포커스가 있다는 사실과 포커스 표시가 보이는 것도 구분합니다. CSS의 :focus는 포커스를 가진 요소에 언제나 일치하고, :focus-visible은 브라우저가 “지금 포커스 위치를 보여줄 필요가 있다”고 판단할 때만 일치합니다. 키보드로 이동했거나 텍스트 입력처럼 키보드로 쓸 요소라면 일치하고, 마우스로 버튼을 눌러 포커스가 생긴 경우에는 보통 일치하지 않습니다. 그래서 포커스 테두리를 :focus-visible에 그리면 마우스 사용자에게는 덜 거슬리면서 키보드 사용자에게는 위치를 알려줄 수 있습니다. 이 교재의 공통 스타일도 그렇게 합니다. outline: none으로 표시를 지울 때는 반드시 다른 뚜렷한 표시로 대신합니다. 프로그램으로 포커스를 옮기면서 화면이 그 요소까지 스크롤되는 것을 막으려면 focus({ preventScroll: true })를 사용합니다.

폼은 이름을 가진 입력들의 현재 값을 수집합니다

폼(form)은 관련된 입력과 제출 동작을 묶는 HTML 구조입니다. 폼의 데이터를 수집할 때는 화면에 보이는 모든 문자열을 긁어오는 것이 아니라, 각 폼 요소가 데이터에 포함될 조건을 충족하는지 확인합니다. 이를 이해해야 사용자에게 보이는 입력과 실제로 읽히는 데이터가 다른 이유를 찾을 수 있습니다.

id는 요소를 찾거나 label의 for와 연결하는 식별자입니다. name은 폼 데이터에서 사용하는 항목 이름입니다. 입력에 id만 있고 name이 없으면 선택자로 찾을 수는 있어도 FormData 항목에는 포함되지 않습니다. 두 속성의 문자열을 같게 쓸 수는 있지만 역할까지 같은 것은 아닙니다.

form.addEventListener("submit", (event) => {
  event.preventDefault();
  const data = new FormData(form);
  const entries = [...data.entries()];
  console.log(entries);
});
  1. 첫 줄은 폼의 submit 이벤트가 발생했을 때 호출할 함수를 등록합니다. 버튼 클릭뿐 아니라 지원되는 키보드 제출 경로도 이 이벤트로 모을 수 있습니다.
  2. 둘째 줄은 이 예제에서 실제 데이터 전송과 페이지 이동이 일어나지 않도록 기본 제출을 취소합니다.
  3. 셋째 줄은 현재 폼을 기준으로 이름과 값의 묶음인 FormData 객체를 만듭니다. 객체를 만드는 것만으로 서버에 전송되지는 않습니다.
  4. 넷째 줄은 항목들을 배열로 펼칩니다. 같은 name이 여러 번 나타나더라도 각각 보존합니다.
  5. 다섯째 줄은 수집된 결과를 확인합니다. 이 배열을 객체로 바로 바꾸면 중복 키의 앞선 값이 덮어써질 수 있습니다.

데이터에 포함될 조건에는 활성 상태도 들어갑니다. disabled인 입력은 일반적으로 포커스를 받지 않고 폼 데이터에서도 제외됩니다. readonly인 일반 텍스트 입력은 사용자가 수정할 수 없지만 포커스를 받고 값을 선택할 수 있으며 데이터에도 포함됩니다. 둘은 단지 회색으로 보이게 하는 두 가지 스타일이 아닙니다.

readonly는 모든 폼 요소에 공통으로 적용되는 속성이 아닙니다. 체크박스에 붙여도 텍스트 입력과 같은 편집 제한을 만들 수 없습니다. 체크박스의 데이터 포함 규칙도 별도로 알아야 합니다. 선택되어 있을 때만 name과 value가 항목으로 들어가며, 해제하면 일반적인 폼 데이터에서 그 항목 자체가 빠집니다. 자동으로 false라는 문자열을 보내는 것은 아닙니다.

현재 값과 돌아갈 기본값은 서로 다른 정보입니다

텍스트 입력의 value는 현재 문자열이고 defaultValue는 기본 문자열입니다. checkbox의 checked는 현재 선택 상태이며 defaultChecked는 기본 선택 상태입니다. 사용자가 입력을 바꾸면 현재 값은 바뀌어도 기본값은 그대로 남을 수 있습니다.

폼의 reset은 각 입력을 이 기본값으로 돌리는 동작입니다. 모든 값을 빈 문자열이나 false로 지우는 기능은 아닙니다. HTML에서 이름의 기본값이 “민지”이고 알림이 checked로 선언되어 있다면 reset 후에도 이름과 켜진 알림이 남습니다. defaultValue를 코드로 바꾸면 이후 되돌아갈 기본값도 달라집니다.

reset 이벤트는 브라우저가 입력에 기본값을 적용하기 전에 발생합니다. 따라서 이벤트 리스너 안에서 바로 value를 읽으면 초기화 전 값일 수 있습니다. 아래 예제는 그 값을 먼저 기록하고, 다음 task에서 기본 동작이 끝난 값을 다시 읽습니다. reset이 취소되었는지도 확인합니다. 이는 모든 이벤트에 무조건 타이머가 필요하다는 뜻이 아니라, 이 이벤트와 기본 동작의 순서를 고려한 연결입니다.

reset은 disabled 같은 모든 속성을 처음 상태로 복구하는 기능도 아닙니다. 입력 값의 초기화와 컴포넌트 전체 설정의 초기화를 따로 설계해야 합니다. 또한 required 입력이 비어 있는 경우처럼 기본 검증에 실패하면 브라우저가 제출을 막아 submit 이벤트까지 도달하지 않을 수 있습니다. 버튼은 눌렸는데 제출 코드가 실행되지 않을 때는 검증 상태도 확인해야 합니다.

접근성 의미와 실제 동작을 함께 제공해야 합니다

시맨틱 의미는 요소가 어떤 역할을 갖는지 나타내는 정보입니다. button, checkbox 같은 네이티브 요소는 브라우저가 역할과 기본 동작을 함께 알고 있습니다. ARIA는 역할이나 상태 같은 접근성 정보를 추가로 표현하는 속성 체계입니다. 하지만 ARIA 속성이 키보드 동작이나 폼 규칙을 대신 구현해주지는 않습니다.

예를 들어 aria-disabled="true"는 비활성 상태라는 의미를 전달하지만, native disabled처럼 클릭을 막거나 폼 데이터에서 값을 빼주지는 않습니다. 마찬가지로 tabindex는 포커스 가능 여부에 관여할 뿐 일반 div를 Enter와 Space로 활성화되는 버튼으로 바꾸지 않습니다. 의미, 포커스, 키보드 처리, 상태 변경은 서로 연결해야 할 별개의 책임입니다.

헤드리스 컴포넌트에서도 먼저 기본 요소가 이미 제공하는 책임을 확인해야 합니다. 그다음 Tabs의 방향키 이동이나 Dialog를 닫은 뒤 원래 버튼으로 돌아가는 동작처럼 추가로 필요한 규칙을 설계합니다. 포커스를 이동할 때는 대상이 문서에 존재하는지, 숨김이나 disabled 상태인지, 다른 코드가 다시 포커스를 옮기고 있는지도 함께 확인합니다.

브라우저는 입력의 제약을 검사할 수 있습니다

required, type="email", minlength, pattern, min과 max 같은 속성은 입력이 지켜야 할 제약을 선언합니다. 제출할 때 브라우저는 폼의 각 입력을 검사하고, 하나라도 어긋나면 submit 이벤트를 발생시키지 않습니다. 대신 첫 번째로 잘못된 입력에 포커스를 옮기고 안내 문구를 보여줍니다. 8-2 예제에서 이름을 비우면 이전 결과가 그대로 남는 이유입니다.

코드에서는 입력의 validity 객체로 어떤 제약을 어겼는지 읽습니다. valueMissing은 필수 값이 빠졌다는 뜻이고, typeMismatch는 이메일이나 URL 같은 형식이 맞지 않는다는 뜻입니다. 모든 제약을 지키면 valid가 true입니다. checkValidity()는 검사 결과를 true나 false로 돌려주고, 어긋난 입력에서 invalid 이벤트를 발생시킵니다. reportValidity()는 같은 검사를 하면서 브라우저의 안내도 보여줍니다. invalid 이벤트는 버블링하지 않으므로 폼에서 모아 들으려면 캡처 단계로 등록합니다.

input.setCustomValidity(taken ? "이미 사용 중인 이름입니다." : "");
form.reportValidity();
  1. 첫 줄은 HTML 속성으로 표현할 수 없는 규칙의 결과를 입력에 알려줍니다. 빈 문자열이 아닌 메시지를 지정하면 그 입력은 잘못된 상태(customError)가 됩니다. 문제가 해결되면 빈 문자열로 다시 지정해야 정상 상태로 돌아옵니다.
  2. 둘째 줄은 폼 전체를 검사하고 첫 번째 문제를 사용자에게 보여줍니다. 검사 결과는 true나 false로 돌려받습니다.

CSS의 :invalid는 페이지를 열자마자 빈 필수 입력에도 일치하므로, 아직 손대지 않은 칸을 오류처럼 보이게 할 수 있습니다. :user-invalid는 사용자가 값을 바꾸었거나 제출을 시도한 뒤에만 일치합니다. 브라우저의 기본 안내 대신 화면에 오류 문장을 직접 보여준다면, 그 문장을 aria-describedby로 입력에 연결하고 aria-invalid="true"를 함께 지정해 보조 기술에도 같은 정보를 전달합니다. form에 novalidate를 붙이면 제출할 때의 자동 검사를 끄고 검사 시점을 코드가 정할 수 있습니다. 어느 경우든 브라우저의 검사는 사용자를 돕는 장치이므로 서버에서도 다시 검사해야 합니다.

더 읽기: MDN · 클라이언트 측 폼 검증, MDN · ValidityState.

하나의 규칙씩 확인하는 예제

8-1 · Tab 순서와 프로그램으로 옮기는 포커스

먼저 예상하기. 제목에 포커스를 보낼 수 있다면 Tab으로도 그 제목에 멈출까요?

프로필 입력 영역

현재 문서의 포커스: 

heading.tabIndex = -1;
heading.focus();
// document.activeElement === heading

관찰할 결과. 제목 이동 버튼을 누르면 제목에 테두리가 나타납니다. 제목의 tabindex="-1"은 프로그램으로 이동할 수 있게 하지만 일반 Tab 순서에는 넣지 않습니다. 제목에서 Tab을 누르면 다음 입력으로 이동합니다. 포커스 표시는 시각 관찰용이며 매 이동을 별도로 읽어주지 않습니다.

8-2 · 화면의 입력과 제출되는 데이터는 다릅니다

먼저 예상하기. readonly, disabled, name 없음 중 어떤 입력이 FormData에 들어갈까요?

아직 폼 값을 읽지 않았습니다.
form.addEventListener("submit", (event) => {
  event.preventDefault();
  const entries = [...new FormData(form).entries()];
});

관찰할 결과. 처음에는 nickname, account, news만 포함됩니다. readonly는 포함되지만 disabled와 name 없는 입력은 제외됩니다. 알림을 해제하고 다시 읽으면 news 항목 자체가 사라집니다. 이름을 비우면 required 검증이 제출을 막으므로 이전 결과가 남습니다.

8-3 · reset은 빈 값이 아니라 기본값으로 돌아갑니다

먼저 예상하기. 이름과 체크를 바꾼 뒤 초기화하면 빈 이름과 꺼진 체크가 될까요?

이름과 체크를 바꾼 뒤 초기화해보세요.
form.addEventListener("reset", (event) => {
  // 이 자리에서는 아직 이전 값일 수 있습니다.
  setTimeout(() => {
    if (!event.defaultPrevented) readCurrentValues();
  }, 0);
});

관찰할 결과. 이름은 “민지”, 체크는 true로 돌아옵니다. 로그의 첫 줄은 reset 이벤트 안의 값, 둘째 줄은 기본 동작 이후 값입니다. 현재값(value, checked)과 기본값(defaultValue, defaultChecked)이 서로 다른 정보이기 때문입니다.

8-4 · 영역은 포커스가 들어오고 나가는 것을 알 수 있을까요?

먼저 예상하기. 아래 영역에 focus 리스너와 focusin·focusout 리스너를 함께 등록했습니다. Tab으로 영역 안의 입력에 들어가면 어느 리스너가 기록할까요? 두 입력 사이를 오갈 때와 영역 밖으로 나갈 때 relatedTarget은 무엇일까요?

검색 조건 영역 
아직 영역에 포커스가 들어오지 않았습니다.
zone.addEventListener("focus", record);   // 버블링하지 않으므로 자식의 포커스는 받지 못합니다
zone.addEventListener("focusin", record);
zone.addEventListener("focusout", (event) => {
  const next = event.relatedTarget;        // 포커스가 갈 요소 또는 null
  const left = next === null || !zone.contains(next);
});

관찰할 결과. 영역의 focus 리스너는 아무것도 기록하지 않습니다. 포커스를 받은 것은 영역이 아니라 안쪽 입력이기 때문입니다. focusin과 focusout은 입력에서 발생해 영역까지 버블링하므로 기록됩니다. 검색어에서 지역으로 이동하면 focusout의 relatedTarget이 지역 입력이므로 “영역 안에서 이동”으로 표시됩니다. 지역에서 영역 뒤 버튼으로 이동하면 “영역 밖으로 나감”입니다. 입력에 포커스를 둔 채 문서의 빈 곳을 클릭하면 relatedTarget은 null입니다. macOS의 일부 브라우저는 버튼을 클릭해도 포커스를 옮기지 않으므로 버튼으로 나가는 경우는 Tab으로 확인하세요.

8-5 · 형식이 틀린 입력은 어떻게 알려질까요?

먼저 예상하기. 이메일 칸을 비우거나 “abc”를 적은 뒤 검사하면 validity의 어떤 값이 true가 될까요? 그 상태로 가입 요청을 누르면 submit 이벤트가 발생할까요?

아직 검사하지 않았습니다.
const ok = input.checkValidity();
const { valid, valueMissing, typeMismatch } = input.validity;
form.addEventListener("invalid", record, { capture: true });

관찰할 결과. 빈 칸은 valueMissing이, “abc”는 typeMismatch가 true입니다. 검사 버튼은 결과만 기록하고 화면에 안내를 띄우지 않습니다. 가입 요청은 브라우저의 안내를 보여주고 포커스를 이메일 칸으로 옮기며 submit을 발생시키지 않습니다. 두 경우 모두 invalid 이벤트 횟수가 늘어납니다. 올바른 주소를 적으면 submit이 기록됩니다.
