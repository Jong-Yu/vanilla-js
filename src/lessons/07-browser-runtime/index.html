7장 · 브라우저의 실행 순서

코드가 실행되는 시간과
화면이 바뀌는 시간

JavaScript가 코드를 실행하는 방식과 브라우저가 그 실행을 배치하는 방식을 구분하면, 이벤트와 DOM의 동작을 시간 순서대로 이해할 수 있습니다.

엔진과 브라우저동기 실행과 호출 스택예약된 실행의 순서DOM과 화면 갱신혼동하기 쉬운 경계동작 예제

JavaScript 엔진과 브라우저는 역할이 다릅니다

JavaScript 엔진은 JavaScript 코드를 해석하고 실행하는 프로그램입니다. 숫자를 더하거나 함수를 호출하고 객체의 값을 읽는 일은 엔진이 담당합니다. 브라우저는 엔진을 포함하면서 문서 표시, 사용자 입력, 네트워크, 타이머 같은 기능도 제공합니다. 둘을 구분해야 “코드를 잠시 멈춘다”와 “다른 일을 예약한다”의 차이를 설명할 수 있습니다.

예를 들어 setTimeout은 JavaScript 문법이 아니라 브라우저 등이 실행 환경에 제공하는 API입니다. 엔진이 이 함수를 호출하면 브라우저는 타이머를 등록하고, 현재 코드는 다음 줄로 진행합니다. 타이머를 기다리는 동안 함수 본문이 그 줄에서 잠들어 있는 것이 아닙니다. 나중에 실행할 함수는 따로 보관되었다가 실행 가능한 시점에 호출됩니다.

DOM도 같은 구분에 속합니다. JavaScript 엔진은 일반적인 객체와 함수의 규칙에 따라 document.querySelector()를 호출하지만, 실제 문서와 요소를 제공하는 쪽은 브라우저입니다. 따라서 브라우저 밖의 JavaScript 환경에 항상 document가 있는 것은 아닙니다. 브라우저의 실행 순서를 배우는 것은 언어 문법에 더해 이 실행 환경의 규칙을 배우는 일입니다.

동기 실행은 호출한 자리에서 끝날 때까지 진행됩니다

동기 실행은 한 작업의 실행이 끝나야 다음 코드로 진행하는 방식입니다. 어떤 함수가 다른 함수를 직접 호출하면, 호출한 함수의 다음 줄로 넘어가기 전에 새로 호출된 함수가 먼저 끝납니다. 이 호출 관계와 돌아갈 위치를 관리하는 구조를 호출 스택(call stack)이라고 합니다.

function inner() { console.log("안쪽"); }
function outer() {
  inner();
  console.log("바깥쪽 계속");
}
outer();

여기서는 outer가 실행되다가 inner를 호출합니다. 스택 위에 inner의 실행이 쌓이고, inner가 끝나면 스택에서 빠지면서 outer로 돌아옵니다. 그래서 “안쪽”을 출력한 다음 “바깥쪽 계속”을 출력합니다. 함수를 새로 만들거나 여러 파일로 나누는 것만으로 실행이 병렬이 되지는 않습니다.

콜백(callback)은 다른 코드가 호출하도록 전달하는 함수입니다. 콜백이라는 이름은 함수의 역할을 설명하며, 실행 시점까지 뜻하지는 않습니다. 배열의 forEach는 항목을 순회하면서 콜백을 동기적으로 호출합니다. 반면 타이머에 넘긴 콜백은 나중에 호출됩니다. “함수를 전달했다”와 “비동기 실행을 예약했다”는 서로 구분해서 읽어야 합니다.

이벤트 리스너에도 이 차이가 있습니다. button.addEventListener("click", handleClick)은 함수를 등록합니다. 이 줄에서 handleClick의 본문은 실행되지 않습니다. 이후 클릭이 발생하면 브라우저가 등록된 함수를 호출합니다. 등록 시점의 코드 흐름과 이벤트가 발생한 시점의 코드 흐름은 같은 실행의 연속이 아닙니다.

브라우저는 실행할 일을 예약하고 순서에 맞춰 꺼냅니다

브라우저의 메인 스레드는 JavaScript 실행과 화면 갱신 등 여러 일을 함께 담당합니다. 어떤 일을 언제 실행할지 조율하는 구조를 이벤트 루프(event loop)라고 합니다. 클릭 처리나 준비된 타이머 콜백처럼 실행할 작업은 task로 다뤄집니다. 현재 실행 중인 동기 코드를 다른 타이머 콜백이 갑자기 끊고 들어오는 방식으로 이해하면 안 됩니다.

microtask는 특정 시점에 우선 처리하는 별도의 대기 작업입니다. Promise의 then 콜백이 대표적입니다. 브라우저는 JavaScript 호출 스택이 비고 정해진 microtask 체크포인트에 도달하면 대기 중인 microtask들을 처리합니다. 보통 한 task가 끝나는 시점이 여기에 포함됩니다. 따라서 “각 JavaScript 문장 사이에 끼어드는 작은 작업”은 아닙니다.

다음 코드는 하나의 클릭 콜백 안에서 실행한다고 생각해보세요. 타이머를 먼저 등록하더라도 Promise 콜백이 먼저 실행되는 이유를 각 줄의 역할로 설명할 수 있습니다.

console.log("시작");
setTimeout(() => console.log("타이머"), 0);
Promise.resolve().then(() => console.log("Promise"));
console.log("끝");
  1. 첫 줄은 현재 동기 실행 안에서 “시작”을 출력합니다.
  2. 둘째 줄은 타이머 콜백을 예약합니다. 콜백 본문을 지금 실행하지 않으므로 다음 줄로 진행합니다.
  3. 셋째 줄은 이미 이행된 Promise에 반응할 콜백을 등록합니다. 이미 결과가 있어도 then 콜백은 즉시 호출되지 않고 microtask로 예약됩니다.
  4. 넷째 줄은 같은 동기 실행의 일부이므로 “끝”을 출력합니다. 이후 이 예제에서는 Promise microtask를 처리하고 나서 타이머 task를 처리합니다.

이 코드의 출력은 “시작 → 끝 → Promise → 타이머”입니다. setTimeout(fn, 0)의 0은 “함수를 지금 호출한다”거나 “정확히 0밀리초 뒤 실행한다”는 약속이 아닙니다. 지연 시간이 지난 뒤 실행할 수 있게 된다는 뜻에 가깝고, 실제 실행 시점은 현재 작업과 브라우저의 스케줄링에 영향을 받습니다.

microtask 처리 중에 새로운 microtask를 추가하면 같은 체크포인트에서 이어서 처리될 수 있습니다. 이 때문에 microtask를 끝없이 추가하면 다음 task나 화면 갱신이 늦어질 수 있습니다. 예약 기능은 실행 순서를 조율하는 수단이지, 많은 계산을 자동으로 다른 스레드에 나눠주는 장치가 아닙니다.

DOM 변경은 객체의 변경이고, 화면 갱신은 그 결과를 보여주는 일입니다

DOM에 값을 대입하면 문서 객체는 즉시 바뀝니다. 바로 다음 줄에서 같은 요소를 읽으면 새 값을 얻습니다. 그러나 새 값을 읽었다는 사실만으로 사용자가 그 모습을 화면에서 봤다고 말할 수는 없습니다. 브라우저는 문서와 스타일을 바탕으로 화면을 갱신하는 과정도 별도로 수행합니다.

label.textContent = "첫 번째";
console.log(label.textContent);
label.textContent = "두 번째";
  1. 첫 줄은 DOM 요소의 내용을 “첫 번째”로 변경합니다.
  2. 둘째 줄은 그 객체의 현재 값을 읽으므로 “첫 번째”를 출력합니다.
  3. 셋째 줄은 같은 요소를 다시 변경합니다. 브라우저가 중간 모습을 표시할 기회를 갖지 않았다면 사용자는 마지막 값인 “두 번째”만 보게 됩니다.

화면을 갱신할 때 브라우저는 필요한 스타일을 계산하고, 요소의 크기와 위치를 정하는 layout을 수행하고, 시각적인 결과를 그리는 paint 등을 처리합니다. 모든 DOM 변경이 매번 전체 layout과 paint를 일으키는 것은 아닙니다. 변경의 종류에 따라 필요한 작업이 다르고, 브라우저는 여러 변경을 모아 처리할 수도 있습니다.

긴 동기 계산은 메인 스레드가 화면을 갱신하거나 입력을 처리할 기회를 늦춥니다. “처리 중”이라는 문구를 대입한 직후 오래 걸리는 반복문을 실행하면, 계산이 끝날 때까지 그 문구가 눈에 보이지 않을 수도 있습니다. DOM 객체를 바꿨다는 사실과 브라우저가 실제로 화면을 그릴 기회를 가졌다는 사실을 나눠 생각해야 합니다.

requestAnimationFrame은 다음 화면 갱신의 paint 전에 호출될 콜백을 예약하는 API입니다. 애니메이션의 위치나 크기를 화면 갱신 주기에 맞춰 바꿀 때 사용합니다. 이미 paint가 끝났다는 알림은 아니며, 비활성 탭에서는 호출이 줄거나 멈출 수 있습니다. 타이머와의 상대 순서나 고정된 호출 간격을 모든 상황에서 보장한다고 생각하지 마세요.

기다려야 하는 조건을 먼저 정해야 합니다

코드가 너무 일찍 실행된 것 같다고 해서 모든 문제에 타이머를 붙이면 원인을 가리기 쉽습니다. HTML 파싱이 끝나 요소가 만들어지기를 기다리는 일, 현재 콜백 이후 상태를 처리하는 일, 화면 갱신에 맞춰 값을 바꾸는 일은 각각 다른 요구입니다. 필요한 조건을 먼저 말로 설명한 뒤 defer, 이벤트, microtask, 타이머, requestAnimationFrame 중 어떤 방식이 맞는지 선택해야 합니다.

또한 “나중에 실행”은 그때도 같은 화면이 존재한다는 보장이 아닙니다. 예약 후 사용자가 화면을 닫았거나 다른 상태로 이동했을 수 있습니다. 아래 두 번째 예제는 실행 번호를 기억해 오래된 예약이 최신 로그를 덮어쓰지 않게 합니다. 이런 수명 관리가 컴포넌트의 연결 해제와 예약 작업 정리로 이어집니다.

첫 예제는 동기 호출, Promise, 타이머의 순서를 기록합니다. 두 번째 예제는 DOM의 중간값을 로그로 남기고 현재 화면의 값과 비교합니다. 로그가 어떤 시점의 값을 읽었는지에 초점을 맞춰 보세요.

7-1 · 동기 실행과 예약된 실행

먼저 예상하기. setTimeout을 Promise보다 먼저 적으면 타이머가 먼저 실행될까요?

log("시작");
setTimeout(() => log("타이머"), 0);
Promise.resolve().then(() => log("Promise"));
log("끝");
아직 실행하지 않았습니다.

관찰할 결과. 동기 코드(1, 2, 3) → Promise(4) → 타이머(5) 순서입니다. 0ms는 현재 실행을 중단하라는 뜻이 아닙니다. 실행할 때마다 로그를 비우므로 반복해서 비교할 수 있습니다.

7-2 · DOM 객체의 값과 화면의 값

먼저 예상하기. 두 번 대입하면 화면에도 중간값이 각각 보일까요?

element.textContent = "첫 번째 값";
console.log(element.textContent);
element.textContent = "두 번째 값";
// DOM은 즉시 바뀌지만 paint가 대입마다 발생하지는 않습니다.

현재 표시: 시작값

아직 실행하지 않았습니다.

관찰할 결과. 로그에는 중간값이 남지만 최종 문구는 “microtask에서 바꾼 값”입니다. requestAnimationFrame의 로그는 paint 완료의 증거가 아니라 갱신 전 콜백의 기록입니다. 화면을 그릴 기회는 브라우저가 정합니다.
