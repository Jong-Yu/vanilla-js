9장 · 의미와 동작을 함께 전달하는 접근성

화면의 변화가
모든 사용자에게 전달되려면

요소가 보인다는 것, 키보드로 조작된다는 것, 보조 기술에 의미가 전달된다는 것은 서로 연결되지만 같은 일이 아닙니다. DOM을 바꿀 때 함께 지켜야 할 이름, 역할, 상태와 포커스의 관계를 살펴봅니다.

이 장에서 이해할 세 가지

  • DOM 트리와 접근성 트리가 왜 일대일로 같지 않은지 설명합니다.
  • 기본 HTML이 제공하는 동작과 ARIA가 표현하는 정보를 구분합니다.
  • 화면, 접근성 상태, 키보드 포커스를 함께 확인합니다.

먼저 읽기: 2장 · DOM 객체, 8장 · 폼과 포커스

DOM과 접근성 트리이름·역할·상태HTML과 ARIA의 책임포커스와 변화 알림네 가지 작은 예제직접 확인하는 방법

같은 문서에서 화면과 접근성 정보를 만듭니다

DOM은 문서의 요소와 텍스트를 객체로 표현합니다. 브라우저는 이 문서의 의미와 표시 상태 등을 바탕으로 보조 기술이 이용할 접근성 트리(accessibility tree)도 구성합니다. 스크린 리더는 화면의 픽셀을 순서대로 읽는 도구가 아닙니다. 브라우저와 운영체제가 제공하는 접근성 정보를 통해 제목, 링크, 버튼 같은 대상을 탐색하고 알립니다.

예를 들어 배치용 요소가 별도의 의미 있는 대상으로 노출되지 않을 수 있습니다. 일반적인 hidden 요소는 화면과 접근성 트리에서 제외됩니다. 반면 aria-hidden="true"는 접근성 정보에서 숨기려는 선언이며 화면 표시나 키보드 포커스를 막는 기능이 아닙니다. 포커스를 받을 수 있는 조작이나 그 조상을 aria-hidden으로 숨기면 조작은 남아 있는데 의미를 찾기 어려운 상황이 생길 수 있습니다.

참고: MDN · 접근성 트리, MDN · aria-hidden

이름은 무엇인지, 역할은 어떤 종류인지, 상태는 지금 어떤지 설명합니다

접근 가능한 이름은 같은 화면의 여러 조작을 구별하는 이름입니다. “이메일 소식 받기”라는 체크박스라면 이름은 “이메일 소식 받기”, 역할은 checkbox, 상태는 선택됨 또는 선택 안 됨입니다. 색이 초록으로 바뀌었다는 사실만으로 이 세 가지 정보가 모두 전달되지는 않습니다.

정보의 종류와 HTML로 표현하는 방법
정보답하는 질문예
이름어떤 조작인가?버튼 안의 글자, 입력과 연결한 label
역할어떤 종류의 요소인가?button, input type="checkbox"의 기본 의미
상태지금 어떤 상황인가?checkbox의 checked, 펼침 버튼의 aria-expanded
설명추가로 알아야 할 내용은?aria-describedby로 연결한 입력 안내

이름은 입력한 값과도 다릅니다. 이름이 “별명”인 입력에 “민지”를 적으면 이름은 계속 “별명”이고 현재 값이 “민지”가 됩니다. 안내 문장을 설명으로 연결하면 짧은 이름을 유지하면서 필요한 정보를 보탤 수 있습니다. placeholder는 입력 중 사라질 수 있으므로 보이는 label을 대신하는 용도로 의존하지 않습니다.

버튼에 보이는 글자가 이미 충분한 이름을 제공한다면 같은 내용을 aria-label로 중복 작성할 필요가 없습니다. aria-label은 기존 이름을 덮어쓸 수 있으므로 화면의 글자와 다른 이름을 만들지 않도록 주의합니다.

참고: WAI · 접근 가능한 이름과 설명

HTML은 기본 동작을 제공하고, ARIA는 의미를 보충합니다

<button>에는 버튼의 의미와 키보드 활성화가 함께 있습니다. 따라서 일반적인 버튼은 click 리스너 하나로 마우스와 키보드로 발생한 활성화를 처리할 수 있습니다. checkbox는 Space로 선택 상태가 바뀌고, 연결한 label도 조작에 사용할 수 있습니다. 필요한 행동을 이미 가진 요소부터 고르면 직접 맞춰야 할 책임이 줄어듭니다.

<button type="button">실행하기</button>
<!-- role="button"을 추가할 필요가 없습니다. -->

ARIA는 동작 코드를 설치하지 않습니다. div에 role="button"을 적어도 Tab 이동이나 Enter·Space 활성화가 자동으로 생기지 않습니다. aria-expanded="true"를 적어도 패널이 저절로 보이지 않습니다. 개발자는 의미로 약속한 상태와 실제 동작을 맞춰야 합니다.

단순한 펼침 영역에는 <details>와 <summary>도 사용할 수 있습니다. 아래 예제는 상태의 연결 원리를 관찰하기 위해 button, aria-expanded, hidden을 직접 연결합니다. 구현의 출발점은 언제나 목적에 맞는 기본 HTML 요소입니다.

참고: WAI · ARIA의 역할은 동작에 대한 약속

변화를 알리는 일과 포커스를 옮기는 일은 다릅니다

포커스는 현재 키보드 입력이 향하는 위치입니다. 체크박스의 선택 상태와는 별개이므로 Tab으로 체크박스에 도착했다고 체크되는 것은 아닙니다. 선택을 바꾼 뒤 다른 요소로 이동해도 체크 상태는 남습니다. 키보드 사용자는 포커스 테두리로 현재 위치를 확인하므로 이를 보이지 않게 지우지 않아야 합니다.

저장 완료 같은 짧은 결과를 알릴 때마다 포커스를 결과 문장으로 옮기면 사용자의 다음 동작이 끊깁니다. role="status"는 현재 작업을 크게 방해하지 않는 상태 메시지에 사용합니다. 기본적으로 polite 알림과 전체 메시지를 읽는 의미를 가지며, 브라우저와 보조 기술이 갱신 내용을 전달할 수 있게 합니다. 메시지 영역을 먼저 문서에 두고 이후 내용을 바꿉니다.

모든 DOM 변경을 live region으로 만들 필요는 없습니다. 체크박스의 기본 상태처럼 이미 전달되는 정보를 다시 알리면 중복될 수 있습니다. 일반적인 결과 안내는 짧은 상태 메시지로, 새 화면으로 이동하는 경우는 새 맥락에 맞는 포커스 관리로 구분해서 설계합니다. 낭독 여부와 시점은 브라우저·보조 기술·설정에 따라 확인해야 합니다.

참고: WAI · 키보드 인터페이스, WAI · 상태 메시지, MDN · status 역할

예제 9-1 · 네이티브 요소와 키보드

click 리스너 하나로 키보드 활성화도 받을 수 있을까?

예상하기 · Tab으로 버튼에 도착한 뒤 Enter 또는 Space를 누르면 실행 횟수가 바뀔까요? 다음 체크박스로 이동하기만 해도 체크될까요?

실행 횟수: 0회

button.addEventListener("click", () => {
  count += 1;
  result.textContent = `실행 횟수: ${count}회`;
});

관찰할 결과 · 버튼은 Enter·Space로 한 번씩 실행됩니다. 체크박스는 포커스만 받아서는 바뀌지 않고 Space로 선택이 바뀝니다. keydown 리스너는 작성하지 않았습니다. 네이티브 버튼에 같은 동작의 keydown까지 더하면 중복 실행될 수 있습니다.

예제 9-2 · 이름, 설명, 현재 값

입력값을 바꾸어도 입력의 이름은 그대로일까?

예상하기 · “별명”이라는 글자를 클릭한 뒤 이름을 적어보세요. 화면의 레이블, 안내, 입력한 값 중 어떤 것이 이 요소의 이름일까요?

다른 학습자에게 보여줄 이름을 적으세요. 실제 이름일 필요는 없습니다.

<label for="accessible-nickname">별명</label>
<input id="accessible-nickname" type="text"
  aria-describedby="nickname-hint" value="민지">
<p id="nickname-hint">다른 학습자에게 보여줄 이름을 적으세요.</p>

관찰할 결과 · 레이블을 클릭하면 입력에 포커스가 갑니다. 입력값을 바꿔도 이름은 “별명”으로 유지됩니다. 개발자 도구의 접근성 패널에서 이름과 설명을 따로 확인하세요. 위 코드는 설명 문장을 줄인 발췌이며, 이 연결에는 JavaScript가 필요하지 않습니다.

예제 9-3 · 표시 상태와 접근성 상태

패널을 펼칠 때 함께 바꿔야 할 정보는 무엇일까?

예상하기 · 버튼을 눌러 내용을 펼치고 다시 접어보세요. hidden과 aria-expanded는 각각 어떤 값을 가져야 할까요?

먼저 결과를 예상하고, 실행한 뒤 코드의 어느 줄이 상태를 바꾸었는지 찾아보세요.

DOM 개념 다시 읽기

aria-expanded="false" · hidden=true

button.addEventListener("click", () => {
  const expanded = button.getAttribute("aria-expanded") === "true";
  button.setAttribute("aria-expanded", String(!expanded));
  panel.hidden = expanded;
});

관찰할 결과 · 펼치면 aria-expanded="true", hidden=false입니다. 키보드로 활성화한 뒤 포커스는 버튼에 남고, 다음 Tab으로 열린 패널의 링크에 갈 수 있습니다. 접은 상태에서는 그 링크가 Tab 순서에 나타나지 않습니다. aria-controls는 관계를 설명하고 실제 표시 변경은 JavaScript가 수행합니다.

패턴 참고: WAI · 펼침 영역(Disclosure)

예제 9-4 · 포커스를 유지하는 결과 안내

결과를 알리기 위해 반드시 포커스를 옮겨야 할까?

예상하기 · 아래 버튼을 키보드로 실행하세요. 결과 문장이 바뀔 때 포커스는 어디에 남아 있어야 다음 실행을 이어가기 쉬울까요?

이 기록은 현재 예제의 메모리에만 남습니다. 페이지를 다시 열면 0회에서 시작합니다.

<p id="practice-status" role="status"></p>

button.addEventListener("click", () => {
  completed += 1;
  status.textContent = `연습 ${completed}회를 기록했습니다.`;
  // focus()를 호출하지 않습니다.
});

관찰할 결과 · 기록 횟수가 증가하고 버튼의 키보드 포커스가 유지됩니다. 스크린 리더에서는 현재 작업을 방해하지 않는 시점에 결과 알림이 전달되는지 확인합니다. 화면의 문구가 바뀌었다는 것만으로 실제 낭독까지 검증한 것은 아닙니다.

같은 기능을 세 가지 관점에서 확인합니다

한 가지 도구만으로 접근성을 모두 확인할 수는 없습니다. 여기서는 아래 순서로 작은 기능의 계약을 확인합니다. 실제 음성 문구와 순서는 스크린 리더, 브라우저, 언어와 설정에 따라 달라질 수 있습니다.

  1. 키보드 · Tab·Shift+Tab으로 조작 사이를 오가며 포커스 위치가 보이는지 확인합니다. 버튼은 Enter·Space, 체크박스는 Space로 조작합니다. 버튼을 Tab으로 찾을 수 없다면 운영체제와 브라우저의 전체 키보드 탐색 설정도 확인합니다.
  2. DOM과 접근성 패널 · 레이블이 입력과 연결되는지, 이름·역할·현재 상태가 맞는지 봅니다. 펼침 예제에서는 aria-expanded와 hidden을 나란히 비교합니다. 이 패널은 정보 확인 수단이며 실제 스크린 리더 동작 전체를 대신하지 않습니다.
  3. 스크린 리더 · 입력의 이름과 설명, 체크박스의 선택 상태, 펼침 버튼의 상태를 구별할 수 있는지 확인합니다. 마지막 예제는 포커스를 옮기지 않고 결과를 들을 수 있는지 확인합니다. 조작할 때는 사용하는 도구의 탐색 모드와 폼 조작 모드도 고려합니다.

접근성은 이 장의 기능만으로 끝나지 않습니다. 제목 구조, 이미지의 대체 텍스트, 색 대비, 확대와 작은 화면에서의 읽기 흐름도 함께 다뤄야 합니다. 이 장에서는 JavaScript로 동작을 연결할 때 직접 영향을 주는 의미와 포커스에 집중했습니다.
