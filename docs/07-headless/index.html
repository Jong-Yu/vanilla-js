헤드리스는 무엇을 분리하는가

이메일 알림을 켜고 끄는 기능을 생각해봅시다. 설정 화면에서는 작은 체크박스이고, 소개 화면에서는 둥근 스위치일 수 있습니다. 둘의 색과 크기가 달라도 “켜짐 또는 꺼짐을 기억한다”, “사용자 조작에 따라 값이 바뀐다”는 규칙은 같습니다. 이 규칙을 특정한 시각 디자인과 분리해 제공하는 방식을 헤드리스라고 부릅니다.

헤드리스 코드는 아무 HTML이나 써도 접근성이 자동 완성되는 마법이 아닙니다. 버튼·입력·레이블 사이의 관계, 키보드 조작, 포커스, 상태를 보조 기술에 전달하는 방식은 여전히 필요합니다. 자유롭게 바꿀 수 있는 시각 표현과, 기능을 제대로 사용하기 위해 지켜야 하는 의미·행동의 규칙을 구분하는 것이 중요합니다.

프레임워크 독립은 또 다른 구분입니다. 특정 프레임워크의 함수나 실행 방식이 없어도 코드를 사용할 수 있다는 뜻입니다. DOM은 브라우저의 기본 API이므로, DOM을 사용하는 코드도 특정 프레임워크에 독립적일 수 있습니다. 상태 계산을 DOM 없이 만들고, 요소를 조작하는 부분을 별도로 두면 두 종류의 코드를 각각 재사용하고 검사하기 쉽습니다.

따라서 “바닐라 JavaScript로 태그를 조작했다”는 사실만으로 분리가 이루어지지는 않습니다. 클릭 함수 안에 값 계산, 특정 요소 찾기, 색 지정이 모두 섞여 있다면 다른 모습에 사용할 때 그 함수를 함께 고쳐야 합니다. 어떤 변경이 어떤 코드에 영향을 주어야 하는지를 생각하며 경계를 정합니다.

상태를 소유한다는 말의 의미

앞 장에서 상태는 현재 화면이 표현할 데이터라고 설명했습니다. 여러 입력이 같은 설정을 보여줄 때 각각의 DOM에서 값을 따로 읽으면 어느 값이 기준인지 모호해집니다. 한쪽은 켜져 있고 다른 쪽은 꺼져 있을 수도 있습니다. 그래서 공유할 값의 기준을 한 곳에 두고, 나머지 요소는 그 값을 표현하게 만들 수 있습니다.

이 기준값과 값을 읽고 바꾸는 기능을 묶어 놓은 객체를 여기서는 저장소(store)라고 부릅니다. 저장소는 언어에 내장된 특별한 종류가 아닙니다. 우리가 만든 일반 객체입니다. 중요한 점은 이름이 아니라, 값의 변경을 어디서 결정하는지가 드러난다는 데 있습니다.

저장소를 사용하는 쪽은 어떤 DOM 요소가 있는지 저장소에 설명할 필요가 없습니다. 저장소에 true를 전달하면 저장소의 선택 상태가 바뀝니다. 그 결과를 두 개의 입력에 보여줄지, 문구 하나로 보여줄지는 연결하는 코드가 정합니다. 이렇게 공개한 함수의 이름과 입력·출력·동작 약속을 API의 계약이라고 생각할 수 있습니다.

작은 저장소를 한 줄씩 읽기

먼저 변경 알림도 없는 가장 작은 형태를 보겠습니다. 이 코드는 DOM에 접근하지 않으며, 값 하나를 보관하는 원리만 담습니다.

function createToggle(initial) {
  let checked = initial;
  return {
    getChecked() { return checked; },
    setChecked(next) { checked = next; }
  };
}
  1. 첫 줄: 함수를 호출할 때 초기값을 initial이라는 매개변수로 받습니다. 함수를 정의하는 것만으로 상태가 생기지는 않습니다.
  2. 둘째 줄: 이번 호출에서 사용할 지역 변수 checked를 만듭니다. 이 변수에 현재 선택 상태를 보관합니다.
  3. 셋째 줄: 바깥에서 사용할 객체를 반환합니다. 객체 안에 적은 두 메서드는 모두 이번 호출의 checked에 접근합니다.
  4. 넷째 줄: getChecked를 호출하면 현재 값을 읽어 반환합니다. 호출한 시점의 값이며, 변수 자체를 외부로 건네는 것은 아닙니다.
  5. 다섯째 줄: setChecked를 호출하면 전달받은 next를 지역 변수에 대입합니다. 아직 문서를 바꾸거나 다른 함수를 호출하지는 않습니다.

createToggle의 실행이 끝나도 두 메서드는 checked에 접근할 수 있습니다. 1장에서 설명한 클로저가 이 관계를 유지합니다. createToggle(false)를 두 번 호출하면 서로 다른 지역 변수를 가진 저장소가 생깁니다. 반대로 같은 저장소 객체를 두 곳에 전달하면 같은 값을 공유합니다.

실제 예제의 createSwitchStore는 이 구조에 입력값 검사, 변경 알림, 초기값으로 되돌리기를 더합니다. 먼저 값을 숨겨 두고 함수로 읽고 바꾸는 이 작은 원리를 이해하면, 추가된 기능이 어느 부분을 확장하는지 따라갈 수 있습니다.

구독은 “바뀌면 호출할 함수”를 등록하는 일

작은 저장소의 setChecked는 값만 바꿉니다. 화면을 자동으로 바꿀 이유가 없고, 화면이 있는지도 모릅니다. 이때 저장소를 사용하는 쪽이 “값이 바뀌면 이 함수를 불러달라”고 요청할 수 있습니다. 이런 등록을 구독(subscription)이라고 부릅니다.

함수를 인수로 전달한다는 점에서는 이벤트 리스너와 같은 JavaScript 개념을 사용합니다. 차이는 누가 함수를 보관하고 호출하느냐입니다. DOM 리스너는 브라우저의 이벤트 시스템에 등록하지만, 이 저장소의 구독은 Set에 함수 객체를 보관합니다. Set은 중복되지 않는 값을 모아 두는 JavaScript 내장 컬렉션입니다. 값 변경 후 그 함수들을 직접 호출합니다. 여기서 호출은 동기적으로 이루어지며 별도의 타이머를 예약하지 않습니다.

const stop = store.subscribe(showState);
store.setChecked(true);
stop();
  1. 등록: showState라는 함수를 전달합니다. 지금 실행한 결과를 전달하는 showState()와 다릅니다. 반환된 stop은 등록을 해제하는 함수입니다.
  2. 변경: 값이 실제로 달라지면 저장소가 구독 중인 showState를 호출합니다. 화면 갱신은 showState가 맡습니다.
  3. 해제: stop을 실행하면 해당 구독만 제거합니다. 저장소나 다른 구독을 모두 없애는 것은 아닙니다.

언제 알림을 보낼지도 계약의 일부입니다. 이 예제는 같은 값을 다시 넣으면 알림을 생략하고, 구독 직후에는 함수를 호출하지 않습니다. 따라서 화면의 최초 표시는 한 번 직접 실행해야 합니다. “구독”이라는 단어만 보고 이런 세부 규칙까지 정해져 있다고 가정하면 처음 화면이나 변경 횟수를 잘못 이해하게 됩니다.

저장소의 getState는 상태 객체를 반환합니다. 이 예제에서는 변경 시 새 객체를 만들고 Object.freeze로 속성 변경을 막습니다. 읽은 객체를 직접 고쳐 변경 알림을 우회하지 않도록 하는 장치입니다. freeze는 얕게 적용되므로 중첩 객체까지 자동으로 고정하지는 않습니다. 현재 예제는 boolean 하나만 보관합니다.

DOM 연결 코드는 두 방향을 이어줍니다

바인딩(binding)은 여기서 저장소와 DOM 요소 사이에 값을 전달하는 연결을 뜻합니다. 입력에서 일어난 change를 저장소에 전달하는 방향과, 저장소에서 바뀐 값을 DOM에 반영하는 방향이 있습니다. 둘을 명확하게 정하면 한 요소의 모양이 달라져도 상태 규칙을 다시 작성하지 않아도 됩니다.

function render() {
  const { checked } = store.getState();
  input.checked = checked;
  input.dataset.state = checked ? "checked" : "unchecked";
}
  1. 상태 읽기: 저장소 객체에서 현재 checked를 꺼냅니다. 객체에서 같은 이름의 속성을 변수로 꺼내는 구조 분해 문법입니다.
  2. 기능 상태 반영: input.checked를 설정해 실제 입력의 현재 선택 상태를 맞춥니다. 사용자가 키보드나 폼으로 다루는 입력의 상태입니다.
  3. 표현할 상태 전달: dataset.state를 문자열로 설정해 data-state 속성을 만듭니다. CSS는 이 값을 조건으로 색이나 모양을 정할 수 있습니다.

반대 방향에서는 change 리스너가 store.setChecked(input.checked)를 호출합니다. 프로그램이 checked에 값을 대입한다고 change가 자동 발생하지 않으므로, 저장소에서 DOM으로 반영하는 작업이 곧바로 change를 다시 발생시키지는 않습니다. 사용자 입력과 프로그램의 값 대입을 구분한 앞 장의 개념이 여기에서 쓰입니다.

브라우저의 체크박스는 클릭과 Space 조작을 이미 제공합니다. 이 예제는 그 기본 동작을 사용하고 바뀐 결과를 읽습니다. 기본 요소를 사용하지 않는 형태로 바꿀 때는 그 요소가 제공하던 키보드·포커스·폼의 계약을 어떻게 유지할지 별도로 설계해야 합니다. 스타일만 없앤 코드와 접근성을 갖춘 재사용 가능한 동작은 같은 완성 수준을 뜻하지 않습니다.
