연결한 코드는
언제까지 남아 있을까

이벤트 등록과 구독은 함수를 나중에 부를 수 있도록 남겨 두는 일입니다. 이 관계가 생기고 끝나는 과정을 이해하면, 화면을 여러 번 열고 닫아도 동작이 겹치지 않게 만들 수 있습니다.

함수가 끝났는데도 동작이 남는 이유

일반 함수를 호출하면 본문을 실행하고 호출한 곳으로 돌아옵니다. 그런데 함수 안에서 addEventListener를 실행했다면 상황이 하나 더 생깁니다. 지금 실행 중인 함수가 끝나더라도, 이벤트 대상에는 나중에 호출할 리스너가 등록되어 있습니다. 등록한 함수의 실행 종료와 등록된 기능의 종료는 다른 시점입니다.

여기서 연결은 어떤 일이 발생했을 때 다른 코드를 실행하도록 만든 관계를 뜻합니다. 클릭과 핸들러 사이의 관계, 저장소 변경과 화면 갱신 함수 사이의 관계가 그 예입니다. 수명(lifetime)은 이 관계를 유지할 기간입니다. 페이지를 보는 동안 필요할 수도 있고, 팝업이 열린 동안에만 필요할 수도 있습니다.

DOM에서 요소를 떼어내는 것 역시 연결을 모두 해제한다는 뜻이 아닙니다. 제거된 요소 객체를 변수가 여전히 가리키면 그 객체를 사용할 수 있습니다. 문서 전체인 document에 등록한 이벤트나 타이머도 따로 남아 있을 수 있습니다. 화면에서 보이지 않는다는 사실과 더 이상 실행될 작업이 없다는 사실은 구분해야 합니다.

JavaScript는 더 이상 도달할 수 없는 객체의 메모리를 자동으로 회수합니다. 이를 가비지 컬렉션이라고 합니다. 그러나 “이 화면이 끝났으니 이 리스너를 그만 사용해야 한다”는 제품의 의미까지 판단해주지는 않습니다. 계속 등록되어 호출 가능한 기능은 필요가 끝나는 시점에 직접 해제해야 합니다. 리스너가 있는 모든 제거된 요소가 반드시 메모리 누수가 된다는 뜻은 아닙니다. 남은 참조와 등록 위치를 함께 봐야 합니다.

같은 코드를 적는 것과 같은 함수를 전달하는 것

1장에서 객체는 내용이 같아도 서로 다른 객체일 수 있다고 배웠습니다. 함수도 객체입니다. 화살표 함수 표현식을 평가할 때마다 새로운 함수 객체가 만들어집니다. 그래서 같은 줄을 두 번 적었다고 같은 리스너를 가리키는 것은 아닙니다.

button.addEventListener("click", () => console.log("클릭"));
button.removeEventListener("click", () => console.log("클릭"));

첫 줄은 어떤 함수 객체 A를 등록합니다. 둘째 줄은 소스 모양이 같지만 새 함수 객체 B를 전달합니다. 브라우저는 등록된 A와 B가 같은 객체가 아니라는 이유로 A를 제거하지 않습니다. 제거할 때는 이벤트 종류, 등록 당시의 함수 객체, capture 설정이 맞아야 합니다.

이 관계를 유지하는 가장 단순한 방법은 함수를 변수나 함수 선언으로 이름 붙이고 같은 값을 등록과 제거에 사용하는 것입니다. 이름의 글자가 중요한 것이 아니라, 두 호출에서 같은 함수 객체를 전달한다는 점이 중요합니다. 이 원리를 이해하면 “removeEventListener를 호출했는데 계속 실행된다”는 문제를 코드의 모양 대신 객체의 동일성으로 설명할 수 있습니다.

정리 함수는 등록한 것을 기억하는 클로저입니다

연결을 만드는 함수가 그 연결을 끝내는 함수도 함께 제공하면 사용하기 편합니다. 보통 이 반환값을 정리 함수(cleanup)라고 부릅니다. cleanup이라는 이름에 자동 기능이 붙어 있는 것은 아닙니다. 우리가 함수 본문에 등록 해제 코드를 적고, 필요한 시점에 호출하는 약속입니다.

function connect(button) {
  function handleClick() {
    console.log("클릭");
  }
  button.addEventListener("click", handleClick);
  return function cleanup() {
    button.removeEventListener("click", handleClick);
  };
}
  1. 첫 줄: 연결할 버튼 객체를 매개변수로 받습니다. 전역 선택자를 함수 안에 고정하지 않아 다른 버튼에도 사용할 수 있습니다.
  2. 둘째~넷째 줄: 이번 연결에서 사용할 핸들러 함수 객체를 만듭니다. connect를 새로 호출하면 새 handleClick이 생깁니다.
  3. 다섯째 줄: 그 함수 객체를 버튼의 click 리스너로 등록합니다. 등록 직후 클릭한 것처럼 실행하지는 않습니다.
  4. 여섯째~여덟째 줄: 같은 버튼과 같은 handleClick을 사용하는 함수를 반환합니다. 이 함수는 바깥 호출이 끝나도 두 값을 기억하므로 나중에 정확한 등록을 제거할 수 있습니다.
const cleanup = connect(button);
// 연결이 필요한 동안 사용
cleanup();

반환받은 함수를 저장하는 줄과 호출하는 줄을 구분해서 읽으세요. connect(button)은 기능을 연결하고 정리 방법을 돌려줍니다. cleanup()은 그 방법을 실제로 실행합니다. 정리 함수를 반환하기만 하고 아무도 호출하지 않으면 연결은 끝나지 않습니다.

한 번 해제된 등록을 같은 조건으로 다시 제거해도 removeEventListener는 아무 일도 하지 않습니다. 그래도 여러 자원을 정리하는 함수라면 두 번 호출해도 상태가 망가지지 않도록 설계하는 편이 좋습니다. 어떤 종료 경로에서 호출되었는지에 따라 서로 다른 결과가 나지 않게 하기 위해서입니다.

연결을 만든 곳이 정리할 대상을 알고 있습니다

앞 장의 bindSwitch는 두 가지 관계를 만듭니다. 하나는 입력의 change를 저장소에 전달하는 DOM 리스너이고, 다른 하나는 저장소 변경을 입력에 반영하는 구독입니다. 둘 중 하나만 해제하면 반대 방향은 계속 동작할 수 있습니다. 따라서 반환하는 정리 함수에서 둘 다 제거합니다.

const unsubscribe = store.subscribe(render);
input.addEventListener("change", handleChange);

return () => {
  unsubscribe();
  input.removeEventListener("change", handleChange);
};

구독 해제와 이벤트 제거는 같은 작업이 아닙니다. 첫째는 우리가 만든 저장소의 함수 목록에서 항목을 지우고, 둘째는 브라우저가 관리하는 리스너 등록을 지웁니다. 정리 함수는 성격이 다른 작업들을 “이번 연결을 끝낸다”는 하나의 목적 아래 모읍니다.

연결을 반복할 때도 같은 관점이 필요합니다. connect를 매번 호출하면 서로 다른 핸들러가 생기므로 한 번 클릭해도 여러 번 처리될 수 있습니다. 예제에서는 현재 연결의 정리 함수를 변수에 보관하고, 이미 연결되어 있으면 다시 연결하지 않습니다. 연결 해제 시 정리 함수를 호출한 뒤 그 변수를 null로 돌려 현재 연결이 없다는 사실을 나타냅니다.

어떤 값이 기능의 상태인지도 구분할 수 있습니다. 저장소의 checked는 알림 설정의 상태이고, cleanupConnection이 null인지 여부는 입력과 저장소가 연결되어 있는지의 상태입니다. 설정이 켜져 있어도 연결은 끊어질 수 있습니다. 서로 다른 사실을 한 boolean으로 표현하려고 하면 조건들이 뒤섞입니다.

예약한 작업에는 나중이라는 시간이 있습니다

타이머를 예약하면 콜백은 현재 함수가 끝난 뒤 나중에 실행될 수 있습니다. 그 사이에 연결이 해제되거나 대상 화면이 사라질 수도 있습니다. 따라서 타이머가 실행될 때까지 기능이 여전히 유효한지 생각해야 합니다. 정리할 때 clearTimeout으로 예약을 취소하거나, 실행 시 현재 연결 상태를 검사하는 이유입니다.

이 예제의 폼 reset은 이런 시간 관계를 보여줍니다. reset 이벤트는 브라우저가 입력을 기본값으로 돌리기 전에 발생합니다. 이벤트 핸들러 안에서 곧바로 현재 checked를 읽으면 아직 초기화 전 값일 수 있습니다. 우리는 브라우저가 기본 동작을 마친 뒤의 값을 저장소에 반영하고 싶습니다.

그래서 reset 핸들러는 setTimeout으로 읽기를 미루고, 정리 함수는 예약된 타이머를 취소합니다. 콜백에서는 연결이 아직 활성인지와 event.defaultPrevented도 확인합니다. 어떤 이벤트가 발생했다고 해서 그 이벤트의 기본 동작이 반드시 수행되는 것은 아니라는 4장의 개념과, 예약 작업의 실행 시점을 다룬 7장의 개념이 함께 쓰입니다.

이 처리를 모든 이벤트에 그대로 복사할 필요는 없습니다. 필요한 것은 값을 언제 읽어야 하는지와 그 사이에 어떤 변화가 가능한지를 구분하는 사고방식입니다. 특히 microtask를 예약했다고 항상 기본 동작 이후를 보장하는 것은 아니므로, 기본 동작이 끝난 값이 필요한 이 예제에서는 다음 task를 사용합니다.

연결을 끊어 보면 각 책임이 드러납니다

아래 입력은 처음 켜져 있습니다. 연결을 끊고 입력을 조작하면 브라우저의 기본 체크 동작은 계속되지만 저장소는 갱신되지 않습니다. 다시 연결하면 저장소 값으로 입력을 맞춥니다. 폼 값 읽기는 저장소가 아니라 실제 입력의 현재 상태를 읽으므로, 두 값의 기준이 서로 다르다는 점도 볼 수 있습니다.

11-1 · 같은 함수로 등록하고 제거하기

먼저 예상하기. 연결을 해제해도 버튼 자체가 비활성화될까요?

function countClick() { count++; }
button.addEventListener("click", countClick);
button.removeEventListener("click", countClick);

관찰할 결과. 연결 버튼을 꺼도 횟수 증가 버튼에는 포커스가 갑니다. 다만 등록했던 함수가 없어 횟수가 늘지 않습니다. 연결과 해제를 반복해도 한 번 누를 때 한 번만 늘어야 합니다.

11-2 · DOM 연결 해제와 브라우저 기본 동작

먼저 예상하기. 연결을 해제하고 체크를 끄면 저장소와 FormData는 같은 값을 읽을까요?

저장소:

상태 변경 알림: 0회

아직 폼 값을 읽지 않았습니다.

관찰할 결과. 연결을 해제하고 체크를 끄면 저장소는 켜짐을 유지하지만 폼에는 notifications가 없습니다. 다시 연결하면 입력은 저장소 값으로 돌아옵니다. 연결 중 초기화하면 기본 체크값과 저장소가 다시 맞춰집니다.

선택 · 연결을 끝내는 시점을 확인하기

연결을 끊고 체크를 바꾼 뒤 저장소 문구와 폼 값을 각각 읽어보세요. 저장소가 갱신되지 않아도 폼 값이 달라지는 이유는 FormData가 읽는 대상이 DOM이기 때문입니다. 연결을 여러 번 반복한 뒤 한 번 조작했을 때 변경 알림이 한 번만 늘면 등록과 정리가 짝을 이루고 있는 것입니다.

코드를 수정해 보고 싶다면 연결 안에서 1초 후 로그를 남기는 타이머를 만들고 cleanup에서 취소해보세요. 정리는 변수 이름이 아니라 실제로 예약한 작업의 ID를 사용해야 합니다.
