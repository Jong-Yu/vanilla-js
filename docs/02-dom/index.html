2장 · HTML에서 DOM 객체까지

문서는 어떻게 객체가 될까요?

HTML 문자열이 DOM 트리가 되는 과정부터 읽습니다. 요소를 찾는 코드는 문서 안의 실제 객체에 접근하는 방법입니다.

DOM의 정의트리가 필요한 이유HTML에서 DOM으로한 줄씩 읽기참조와 검색 범위목록의 의미

DOM은 문서를 다루기 위한 객체 모델입니다

HTML 파일은 처음에는 글자들의 나열입니다. <h1>제목</h1>이라는 문자열에 제목의 시작과 끝을 표시할 수 있지만, 문자열 자체가 클릭되거나 부모 요소를 알고 있는 것은 아닙니다. 브라우저는 HTML을 읽어 요소와 텍스트를 객체로 만들고, 이 객체들을 문서 구조에 맞게 연결합니다. 이 구조와 그것을 다루는 인터페이스가 DOM, 즉 Document Object Model입니다.

DOM을 “JavaScript로 작성한 HTML”이라고 생각하면 역할이 섞입니다. HTML은 문서를 기술하는 형식이고, DOM은 실행 중인 문서를 객체로 표현하는 모델입니다. JavaScript는 DOM 객체에 접근할 때 사용하는 언어입니다. const나 함수는 JavaScript 문법이지만, document.querySelector()는 브라우저가 제공하는 DOM API를 호출하는 코드입니다.

DOM은 화면에 보이는 그림 자체도 아닙니다. 브라우저는 DOM, CSS 등 여러 정보를 바탕으로 요소의 크기와 위치를 계산하고 화면을 그립니다. CSS로 보이지 않게 한 요소도 DOM 안에 남아 있을 수 있습니다. 아직 문서에 붙이지 않은 요소 객체 역시 존재할 수 있습니다. 객체의 존재, 문서와의 연결, 화면 표시를 구분하면 이후 생성과 삭제를 더 정확히 이해할 수 있습니다.

왜 문서를 객체의 트리로 만들까요?

문서의 어느 부분을 바꾸려 할 때 HTML 문자열 전체에서 글자를 찾아 교체하면 구조를 안정적으로 다루기 어렵습니다. 같은 글자가 여러 곳에 있을 수 있고, 태그가 중첩되며, 사용자의 입력이나 프로그램에 의해 현재 상태가 달라질 수도 있습니다. 이름표가 있는 실제 요소 객체를 찾아 조작할 수 있다면 이런 문제를 문서 전체의 문자열 편집으로 풀 필요가 없습니다.

HTML은 요소 안에 다른 요소를 넣는 중첩 구조입니다. 브라우저는 이것을 부모와 자식 관계로 나타냅니다. 하나의 노드에서 아래로 연결된 자식들을 따라갈 수 있는 구조를 트리라고 부릅니다. 한 요소의 자식은 바로 아래에 붙은 노드이고, 후손은 그 자식의 자식까지 포함한 모든 아래쪽 노드입니다. 같은 부모를 가진 노드들은 형제 관계입니다.

트리라는 모델이 있으면 “이 영역 안의 버튼”, “현재 항목의 부모 목록”, “이 제목의 다음 형제”처럼 관계로 대상을 설명할 수 있습니다. 문서 순서, 요소 검색, 이벤트가 전달되는 경로도 이 구조를 토대로 합니다. DOM을 배운다는 것은 명령 이름을 외우기 전에, 어떤 객체가 어디에 연결되어 있고 어느 대상을 변경할지 파악하는 법을 배우는 것입니다.

HTML이 객체와 관계로 바뀌는 과정

브라우저의 HTML 파서는 입력 문자열에서 시작 태그, 끝 태그, 텍스트 등의 의미를 읽고 문서 트리를 구성합니다. section 안에 h2와 ul이 있으면 section 객체의 자식 관계로 두 요소가 연결됩니다. ul 안의 li들은 ul의 자식입니다. 태그 사이에 적힌 글자는 별도의 텍스트 노드가 됩니다. 따라서 요소만 그린 구조도와 실제 모든 노드를 포함한 DOM은 세부 모습이 다를 수 있습니다.

<section id="profile">
  <h2>학습할 주제</h2>
  <ul><li>DOM</li><li>이벤트</li></ul>
</section>

이 조각에서 section의 직접 자식 요소는 h2와 ul입니다. li는 section의 후손이지만 직접 자식 요소는 아닙니다. “학습할 주제”라는 글자는 h2의 자식 텍스트 노드입니다. 들여쓰기와 줄바꿈도 텍스트 노드가 될 수 있으므로, 요소 사이에 공백 노드가 생길 수 있습니다. 공백을 화면에서 뚜렷하게 보지 못하더라도 문서 객체에는 남을 수 있습니다.

DOM을 구성하는 공통 단위를 Node라고 합니다. 문서 Document, 요소 Element, 글자를 담는 Text 등은 서로 다른 종류의 Node입니다. Element는 HTML에만 한정되지 않는 요소의 공통 기반입니다. HTML 요소는 HTMLElement 계열, SVG 요소는 SVGElement 계열이며 모두 Element에 해당합니다. 그러므로 Node와 Element는 같은 말이 아니고, Element와 HTMLElement도 범위가 다릅니다.

객체가 제공하는 기능은 종류에 따라 다릅니다. 요소에는 classList처럼 요소를 위한 기능이 있지만 텍스트 노드에는 없습니다. children은 자식 요소만 읽고, childNodes는 텍스트와 주석 등을 포함한 자식 노드를 읽습니다. parentElement는 부모가 요소일 때 반환합니다. html 요소의 부모는 문서이므로 parentNode는 document여도 parentElement는 null입니다.

브라우저가 파싱하며 생략된 구조를 보완하거나 잘못 중첩된 HTML을 정리할 수도 있습니다. 그래서 실행 중인 구조를 확인할 때는 파일의 글자뿐 아니라 개발자 도구의 Elements도 살펴봅니다. 이 장의 외부 스크립트는 defer로 연결되어 있으므로 초기 HTML 파싱이 끝난 뒤 요소를 찾습니다. 검색 코드는 대상이 실제로 생성된 시점 이후에 실행되어야 합니다.

객체를 찾고 읽는 코드를 한 줄씩 읽기

DOM API의 property는 객체에서 값을 읽거나 쓰는 창구이고, method는 객체가 제공하는 작업을 호출하는 함수입니다. title.textContent는 property 읽기이고 area.querySelector("h2")는 method 호출입니다. 점 뒤에 어떤 이름을 쓰느냐보다, 지금 대상이 어떤 객체이며 읽는지 호출하는지를 구분하는 것이 먼저입니다.

const area = document.querySelector("#profile");
const title = area.querySelector("h2");
const savedText = title.textContent;
title.textContent = "새로운 주제";
  1. 1행: 문서에서 id가 profile인 첫 요소를 찾습니다. 반환된 section 객체를 area라는 이름으로 가리킵니다. HTML 문자열을 복사한 것이 아닙니다.
  2. 2행: area의 후손 중 첫 h2 요소를 찾습니다. title은 찾은 h2 객체를 가리키며, area와는 다른 객체입니다.
  3. 3행: h2의 텍스트 내용을 문자열로 읽어 savedText에 저장합니다. 이 변수에는 요소 자체가 아니라 그 시점에 읽은 글자가 들어갑니다.
  4. 4행: 같은 h2 객체의 내용을 새로운 문자열로 교체합니다. 문서 속 제목은 바뀌지만 savedText에 이미 저장된 문자열까지 다시 읽히지는 않습니다.

여기서 첫 검색에 실패하면 area는 null입니다. null은 빈 요소 객체가 아니라 대상이 없다는 값이므로 다음 줄에서 메서드를 호출할 수 없습니다. 이 짧은 예제는 해당 HTML이 존재함을 전제로 합니다. 실제 프로그램에서는 필수 구조를 보장하거나, 결과를 검사하고 없는 경우의 흐름을 정해야 합니다. 검색 실패와 객체 수정 실패는 서로 다른 단계의 문제입니다.

HTML 문자열, 요소 참조, 검색 범위를 구분하기

같은 요소를 두 번 검색하면 두 변수로 같은 DOM 객체를 가리킬 수 있습니다. 한 변수로 속성을 수정하면 다른 변수에서 읽어도 바뀐 값을 봅니다. 반면 area.outerHTML처럼 요소를 HTML 문자열로 표현해 읽으면 문자열 결과를 얻습니다. 그 문자열을 변수에 저장했다고 요소와 계속 연결되는 것은 아닙니다. 이후 DOM을 변경해도 앞서 저장한 문자열은 그때 읽은 결과로 남습니다.

실행 중인 DOM을 바꾸는 작업은 원본 HTML 파일을 편집하는 작업과도 다릅니다. JavaScript가 제목을 변경해도 디스크의 파일에 그 문장이 저장되지는 않습니다. 페이지를 다시 실행하면 소스에서 새 문서가 만들어지고 코드가 다시 실행됩니다. 파일, 현재 DOM 객체, DOM에서 읽어 얻은 문자열은 각각 다른 시점과 역할을 갖습니다.

선택자는 찾을 요소의 조건을 적는 문자열입니다. #profile은 id, .topic은 class, li는 요소 이름을 조건으로 사용합니다. 검색은 이 문자열을 해석해 실제 객체를 돌려줍니다. 선택자 문자열 자체를 바꾼다고 문서의 id나 class가 바뀌지는 않습니다. 문서 전체에서 검색할 수도 있고, 이미 찾은 영역 안으로 반환 대상을 좁힐 수도 있습니다.

area.querySelector("li")는 area 내부의 첫 li 후손을 찾습니다. 중첩된 목록이 있으면 바로 아래뿐 아니라 더 깊은 요소도 포함될 수 있습니다. :scope > ul처럼 쓰면 검색 기준인 area의 직접 자식 ul을 고릅니다. 요소에서 검색할 때 그 요소 자신은 반환 대상에 포함하지 않습니다. 자신의 조건 일치 여부를 알고 싶을 때는 matches를 사용합니다.

선택자가 문법상 유효하지만 일치하는 요소가 없으면 querySelector는 null을 반환합니다. 잘못된 CSS 선택자 문법은 예외를 일으킵니다. 코드가 예상과 다를 때는 대상이 없는지, 검색 범위를 잘못 정했는지, 문법이 틀렸는지를 나누어 보면 됩니다. 나중에 생성될 요소를 너무 일찍 찾은 경우도 “없음”으로 나타납니다.

정적인 목록은 요소를 얼려 놓은 복사본이 아닙니다

querySelectorAll()은 일치하는 여러 요소를 담은 NodeList를 반환합니다. 하나만 일치해도 목록이고, 하나도 없으면 길이가 0인 목록입니다. 요소 하나의 참조와 요소 목록은 다르므로, 목록의 항목을 꺼내거나 반복하면서 실제 요소를 다뤄야 합니다. 빈 목록도 객체이므로 단순히 값이 존재하는지만 검사해서는 검색 성공을 판단할 수 없습니다.

querySelectorAll의 목록은 검색 시점의 구성원을 유지하는 정적 목록입니다. li가 두 개일 때 목록을 받아둔 뒤 세 번째 li를 추가해도 기존 목록의 길이는 2입니다. 새 검색을 해야 세 개를 얻습니다. 하지만 기존 목록 안의 li 객체는 실제 문서 요소의 참조입니다. 그 요소의 글자를 바꾸면 화면도 바뀝니다. “어떤 객체가 목록에 들어 있는가”가 고정되며, 객체의 내용까지 복사하거나 고정한 것은 아닙니다.

반면 list.children은 현재 자식 요소를 반영하는 실시간 컬렉션입니다. 같은 변수를 통해 읽어도 자식이 추가되면 길이가 바뀝니다. 모든 NodeList가 정적인 것도 아닙니다. childNodes는 실시간 NodeList입니다. 이름에 List가 있다는 이유로 갱신 방식을 추측하지 말고 어떤 API가 만든 목록인지 확인해야 합니다. 고정된 작업 대상이 필요한지, 늘 현재 구조가 필요한지에 따라 적합한 읽기 방법이 달라집니다.

이제 DOM 검색은 문자열로 화면 일부를 긁어오는 작업이 아니라, 문서 트리 안에 있는 객체와 관계에 접근하는 작업으로 볼 수 있습니다. 다음 장에서는 얻은 객체의 어떤 부분을 바꾸면 현재 입력값, 내용, CSS와 연결되는 상태가 달라지는지 살펴봅니다.
