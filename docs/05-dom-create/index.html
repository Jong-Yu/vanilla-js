노드 객체와 문서의 연결은 별개의 개념입니다

DOM은 문서를 객체들의 관계로 표현합니다. 이 구조에 참여하는 객체를 노드라고 하며, 요소와 텍스트는 서로 다른 종류의 노드입니다. li 요소를 만든다는 것은 메모리에 그 요소를 나타내는 객체를 만든다는 뜻입니다. 객체를 만들었다는 사실만으로 현재 문서의 목록에 항목이 하나 생기는 것은 아닙니다.

문서의 구조를 이루는 것은 객체의 존재뿐 아니라 객체 사이의 부모·자식 관계입니다. 어느 ul의 자식으로 li를 연결하면 그 li가 해당 목록에 속하게 됩니다. 연결하기 전의 li는 이미 속성과 자식을 가질 수 있지만, 아직 화면의 문서와 연결되지 않았습니다. 이를 문서에서 분리된 상태라고 생각하면 됩니다.

문서에 연결되는 것과 실제 화면에 보이는 것도 완전히 같은 말은 아닙니다. 브라우저는 DOM과 CSS 등을 바탕으로 요소의 크기와 위치를 계산하고 화면을 그립니다. 이 과정을 렌더링이라고 합니다. 문서에 연결되어 있어도 숨김 스타일이 적용되면 보이지 않을 수 있고, DOM 변경 직후 자바스크립트에서 구조를 읽을 수 있다는 사실이 그 순간 화면 그리기까지 끝났다는 뜻은 아닙니다.

객체를 만든 뒤 연결하는 방식이 필요한 이유

HTML 파일에는 처음부터 알고 있는 구조를 선언할 수 있습니다. 하지만 사용자가 새 주제를 입력할 때마다 항목이 늘어나는 화면은 나중에 문서 구조를 바꾸어야 합니다. 자바스크립트가 새 객체를 만들고 기존 부모에 연결하면, 처음 HTML에 없던 항목도 문서에 추가할 수 있습니다.

생성과 연결을 나누면 화면에 붙이기 전에 작은 구조를 조립할 수 있습니다. 목록 항목을 위한 li를 만들고, 이름을 보여줄 span과 삭제할 button을 그 안에 넣은 다음 완성한 li를 목록에 붙이는 방식입니다. 이 순서는 어떤 요소가 무엇을 포함하는지 코드에 드러나게 합니다. 데이터가 준비되지 않은 반쪽 구조를 여러 위치에서 고치는 대신 한 항목을 구성하는 책임을 한 함수로 모을 수도 있습니다.

이 단계에서 중요한 것은 API 이름을 많이 기억하는 일이 아니라, 각 문장이 객체를 만드는지, 내용을 바꾸는지, 연결 관계를 바꾸는지 구분하는 일입니다. 화면에 보이지 않는 문제가 생겨도 객체 생성의 실패인지, 연결 누락인지, 스타일의 문제인지 나누어 살펴볼 수 있기 때문입니다.

문서 구조를 조립하는 실행 흐름

document.createElement("li")는 li 요소 객체를 반환합니다. 변수에 담으면 그 변수가 객체를 가리키며, textContent 같은 속성을 바꾸어 내용을 채울 수 있습니다. 부모의 append에 요소를 전달하면 부모의 마지막 자식으로 연결됩니다. append는 새 객체를 만드는 명령이 아니라 이미 있는 객체의 위치를 정하는 명령입니다.

목록 예제는 입력값에서 앞뒤 공백을 제거하고 비어 있지 않은지 확인한 다음 요소를 만듭니다. 사용자에게 보여줄 문구는 span의 textContent에 넣습니다. 삭제 버튼은 button으로 만들고 type을 button으로 지정합니다. 이 버튼의 의미는 목록 항목 삭제이며, 폼 안에 놓이더라도 원치 않는 제출을 시작하지 않도록 역할을 분명히 하는 것입니다.

그다음 이름과 버튼을 li에 연결하고, li를 ul에 연결합니다. 이때부터 문서의 검색으로 새 항목을 찾을 수 있습니다. 마지막으로 항목 수 안내를 갱신하고 입력창을 비웁니다. 자식 요소의 개수가 변했다고 별도의 안내 문구까지 자동으로 바뀌는 것은 아니므로, 구조 변경과 안내 갱신을 순서대로 실행합니다.

부모가 자식의 행동을 관리하는 방식

항목을 만들 때마다 삭제 버튼에 함수를 연결할 수도 있습니다. 여기서는 목록 부모에 click 리스너를 한 번 연결하고, 자식에서 올라온 클릭을 처리합니다. 이벤트의 버블링을 이용해 여러 자식의 처리를 부모에게 맡기는 방식을 이벤트 위임이라고 합니다. 부모 리스너는 새 자식이 추가되기 전부터 존재하므로, 나중에 생긴 버튼도 같은 규칙으로 처리할 수 있습니다.

부모가 모든 클릭을 삭제로 처리하면 안 됩니다. 실제로 누른 대상인 event.target에서 삭제 버튼을 찾아야 합니다. 버튼 안에 span이나 아이콘이 들어갈 수 있으므로, target 자체부터 조상 방향으로 조건에 맞는 요소를 찾는 closest를 사용합니다. 찾은 버튼이 현재 목록 안에 있는지 확인한 뒤 그 버튼이 속한 li를 제거합니다. 위임은 자식별 등록을 줄여주지만, 처리할 대상을 정확히 판별하는 책임을 부모에 둡니다.

네 줄로 보는 생성과 연결

아래 코드에서 list는 이미 문서에 있는 ul 요소를 가리킨다고 가정합니다. 문자 “DOM 익히기”가 곧바로 화면에 나타나는 것이 아니라, 객체의 내용이 된 다음 문서에 연결됩니다.

const item = document.createElement("li");
item.textContent = "DOM 익히기";
list.append(item);
item.remove();
  1. 첫 줄은 새 요소 객체를 만듭니다. item은 그 객체를 가리키는 변수이고, 아직 list와 부모·자식 관계가 없습니다.
  2. 둘째 줄은 객체의 내용을 텍스트로 채웁니다. 요소 안에 텍스트 노드가 생기지만 item 자체는 여전히 문서 밖에 있습니다.
  3. 셋째 줄은 item을 list의 마지막 자식으로 연결합니다. 이 뒤에 list.children을 읽으면 추가된 항목이 포함됩니다.
  4. 넷째 줄은 item을 부모에서 떼어냅니다. item 변수는 여전히 같은 객체를 가리키며, 내용도 읽을 수 있습니다. 다시 append하면 그 객체를 다시 연결할 수 있습니다.

위 네 줄을 한 번에 실행하면 추가 직후 제거되므로 사용자에게 중간 상태가 보이지 않을 수 있습니다. 자바스크립트는 연결과 제거를 모두 수행했지만, 브라우저가 화면을 그릴 때는 이미 제거된 구조를 볼 수 있기 때문입니다. 문서 구조가 바뀐 순서와 사용자가 눈으로 본 프레임을 같은 것으로 생각하지 않는 것이 중요합니다.

같은 모양, 같은 객체, 복사된 객체

내용이 똑같은 li 두 개도 각각 createElement로 만들었다면 서로 다른 객체입니다. 반대로 하나의 item을 여러 변수에 담아도 객체가 복제되지는 않습니다. 두 변수가 같은 대상을 가리킬 뿐입니다. 객체가 바로 그 객체라는 성질을 정체성이라고 하며, DOM을 다룰 때 위치나 모양과 구분해야 합니다.

같은 요소를 다른 부모에 append하면 기존 자리에서 빠져 새 자리로 이동합니다. 같은 부모에 다시 append하면 맨 뒤로 이동합니다. 한 객체가 문서의 두 위치에 동시에 놓일 수는 없습니다. 여러 항목을 만들려는 반복문에서 요소 하나만 만들어 계속 붙이면, 항목 수가 늘지 않는 이유도 여기에 있습니다. 이동은 객체 자체를 유지하므로 그 객체에 직접 연결한 이벤트 리스너도 유지됩니다.

별개의 복사본이 필요하면 cloneNode를 사용할 수 있습니다. true를 전달하면 자식까지 복사하며 복사본은 원본과 별도의 객체입니다. 원본을 바꾸어도 복사본이 자동으로 따라 바뀌지는 않습니다. 속성도 복사되므로 id가 있다면 같은 문서에서 중복되지 않게 바꾸어야 합니다. addEventListener로 등록한 리스너는 복사되지 않습니다. 다만 부모에 위임한 이벤트는 복사본도 부모 안에 들어오면 같은 규칙으로 처리할 수 있습니다.

텍스트를 넣는 일과 HTML을 해석하는 일

textContent는 문자열을 글자로 넣습니다. 사용자가 <strong>안녕</strong>이라고 입력해도 strong 요소를 만들지 않고 꺾쇠까지 표시합니다. 반면 HTML로 해석해서 넣는 방식은 문자열을 구조로 바꿉니다. 사용자가 입력한 이름처럼 내용만 필요한 경우에는 textContent를 사용하면 입력이 의도하지 않은 문서 구조가 되는 일을 피할 수 있습니다.

textContent를 부모 li에 대입하면 기존 자식이 텍스트로 교체된다는 점도 기억해야 합니다. 이름과 삭제 버튼을 이미 붙인 뒤 li.textContent를 바꾸면 버튼도 사라집니다. 항목의 이름만 바꾸려면 이름을 맡은 span의 내용을 수정해야 합니다. 어떤 객체의 어느 부분을 바꾸는지가 결과를 결정합니다.

현재 구조와 예전에 검색한 목록

querySelectorAll은 검색한 시점의 결과를 담은 정적인 NodeList를 반환합니다. 나중에 항목을 추가해도 전에 얻어둔 목록의 길이는 늘지 않습니다. 반면 부모의 children은 현재 자식 요소의 변화를 반영하는 목록입니다. 어떤 컬렉션을 읽는지에 따라 “항목 수”의 기준 시점이 달라집니다. 현재 개수가 필요하면 다시 검색하거나 현재 children을 읽어야 합니다.

      예제 5-3 · 개념 조합 · 생성 + 연결 + 이벤트 위임
      나중에 생긴 버튼의 클릭은 누가 받을까요?
      

      예상하기: 삭제 리스너는 목록에 한 번만 등록했습니다. 새 주제를 추가해도 그 항목의 삭제 버튼이 동작할까요?
      

      

        

        list.addEventListener("click", (event) => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest("button[data-action='remove']");
  if (!button || !list.contains(button)) return;
  // 버튼이 속한 항목을 찾고, 다음 포커스를 정한 뒤 제거합니다.
});
        

        관찰할 결과: 새 항목도 같은 부모를 통해 삭제됩니다. 글자 부분을 누르면 삭제되지 않습니다. 삭제 버튼에는 주제 이름을 포함한 접근 가능한 이름이 있습니다. 키보드로 삭제하면 다음 항목, 없으면 이전 항목의 삭제 버튼으로 이동하며, 목록이 비면 입력으로 돌아갑니다.
        

        실행 순서: 주제를 입력하고 Enter → 새 항목의 삭제 버튼까지 Tab → Enter로 삭제 → 포커스가 이어지는 위치 확인. 입력한 태그 모양의 문자열도 문서 구조가 아닌 글자로 표시됩니다.
